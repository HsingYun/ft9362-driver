# FT9362 Windows / Linux 行为差异与移植参考

Windows 静态核对：2026-10-11 至 2026-10-12；Linux 对照更新：2026-10-12。对象：本工程的 USB `2808:0752` FT9362 开发驱动，以及用户提供的 Windows 5.2.69.24 安装包。

本文独立保存协议、时序、数据布局、调用条件和差异，不要求读者另外打开 Windows 文件才能理解已经恢复的行为。**它不是厂商协议规格，也不是已在 FT9362 实机上验证的完整驱动配方。** 没有恢复的部分集中列在第 14 节；平台 ACPI 行为、图像处理的逐像素一致性等仍需验证，不能写成已经解决。本机支持范围见[设备能力](device-capability.md)。

只排除 Windows 的身份匹配算法内部实现。图像解密、灰度预处理、采集质量判断、录入流程接口、模板存储边界、电源与恢复机制仍在范围内。Windows 代码的静态能力与本机 USB 实测分别记录，不将共享路径直接视为本机已支持。

阅读顺序：先读第 1–2 节确定型号与差异范围；实现通信看第 3–6 节；处理图像看第 7–8 节；实现电源/恢复看第 9 节。第 10–11 节记录条件固件与平台集成，第 12–14 节列出不可照搬的行为、验收方法和剩余缺口，第 15 节用于审计定位。

本机报告 HT32 控制器版本和 40×152 尺寸；普通与扩展取图可用。应用唤醒、UID 等查询返回 09，模式与深睡恢复前提未满足。扩展通道成功不代表其他共享命令可用。

## 2. 整体架构与能力差异

Windows 的主机链路为：

```text
Windows 生物识别服务
  ├─ 系统 SensorAdapter → WBDI 请求 → UMDF 主 DLL → USB 桥接固件 / 传感器
  ├─ 厂商 EngineAdapter ← 8 位灰度图与 BIR 格式
  └─ 系统 StorageAdapter ← 厂商导出的模板

另外：电源通知、ACPI/EC、私有 IOCTL、诊断及条件固件升级
```

Linux 当前链路为：

```text
Python / libfprint API
  → FpDevice 子类 → 串行 FpiSsm → 同步检查及普通 / 扩展查询与取图
  → 完整 12166 字节帧 → 无 GLib 的 C ABI / libfocaltech.0752.algo.so
  → FpPrint 的 (格式字符串, 字节数组)
```

| 项目 | Windows 样本 | 当前 Linux | 移植含义 |
| --- | --- | --- | --- |
| 设备匹配 | 同时安装到 0752、C652 | 只匹配 0752 | 保持目标边界，不能顺带加入 C652 |
| USB 管道 | 接口 0，枚举两个管道并按 Bulk 方向选择 | 接口 0，固定 IN=81、OUT=03 | Windows 不提供可直接抄出的端点常量 |

## 3. USB 传输层

证据：`M:F048`、`M:E814`、`M:EB38`、`M:EEC0`。

Windows 建立 USB target，选择接口 0，要求接口有 **两个管道**，枚举 Bulk 类型并分别寻找输入与输出方向。读取输入最大包长度用于缓冲区对齐；还读取 HighSpeed、SelfPowered、RemoteWakeable 等设备 traits。

| 项目 | Windows | Linux |
| --- | --- | --- |
| 执行方式 | WDF 同步收发，专用线程，互斥锁/临界区串行化 | GLib 主循环上的异步 FpiUsbTransfer |
| OUT 超时 | 200 ms | 1000 ms |
| IN 超时 | 2000 ms | 从 OUT 完成起计，单条响应总预算：健康 / 状态 1000 ms，图像 5000 ms |
| 协议层重试 | 失败传输最多追加 3 次，即至多 4 次尝试 | 不自动重发 |
| IN 容量 | 将协议请求长度按输入最大包长度向上取整 | 剩余接收上限按 64 对齐；健康、状态和图像响应首次均为 12224 |
| 收包 | 请求一次 BulkRead，再按协议需求解释 | 按实际长度有界累积，完整校验；普通帧保持 12166 字节契约 |
| 连续传输错误 | 同方向错误计数超过 3，调用恢复；成功时清计数 | 单次传输错误即标记待同步并结束当前动作 |
| 恢复动作 | 顺序重置 IN 管道、OUT 管道、USB 端口 | 下一动作有界排空并检查健康；无主动 pipe/port reset |

若端点最大包长度为 64，Windows 图像请求 `12165` 会向上取整到 `12224`，状态请求 `6` 会向上取整到 `64`。这里的 64 是条件示例，并不是从 DLL 硬编码中恢复的设备描述符。

**Windows 实现的缺陷也必须保留为差异记录：** 底层拿到了实际读取长度，却仍按上层请求长度复制；OUT 成功时没有对应 Linux 的短写校验。这些缺陷不能成为 Linux 的兼容目标。重发写命令还可能重复触发操作，移植时必须判断命令是否允许重试。

`ReadData` 调用中出现的 `1` / `7`，没有证据表明在最终 BulkRead 中决定超时或重试次数，不能命名成“1 秒 / 7 秒”。

## 4. 协议封装、响应与错误

### 4.1 通用封装

请求，证据 `M:DD10`：

```text
02 | L_hi L_lo | CMD | 参数 N 字节 | BCC
L = N + 1                 # 命令字 + 参数
总字节数 = L + 4
BCC = XOR(长度两字节、CMD、所有参数)
```

响应，证据 `M:DE70`：

```text
02 | L_hi L_lo | STATUS | 数据 D 字节 | BCC
L = D + 1                 # 状态 + 数据
逻辑总字节数 = L + 4 = D + 5
BCC = XOR(长度两字节、STATUS、所有数据)
```

长度为大端，XOR 不包含起始 `02` 和 BCC 自身。应用载荷内部的字节序另行定义，不能由头部大端推断所有字段都大端。

通用成功 ACK：`02 00 01 04 05`。数据值为 00 的逻辑响应：`02 00 02 04 00 06`；数据值为 01 的逻辑响应：`02 00 02 04 01 07`。这些是按解析器重建的示例，不是本轮实机抓包。

### 4.2 Windows 解析顺序及不足

1. 按调用方数据容量 D 请求 D+5 字节的逻辑响应，底层执行对齐后的 BulkRead。
2. 取大端 L；若 `L > D+1`，返回 `0xC0000206`；若 L=0，返回 `0xC0000186`。
3. 输出实际数据长度 `L-1`。
4. STATUS 不是 04 时保存状态字节并返回 `0xC00000E5`，这条错误分支不会继续检查 BCC。
5. 调用方要求数据且返回数据为空时，返回协议错误。
6. 从偏移 4 复制数据，再比较 BCC；不一致返回 `0xC0000229`。

它不是先读固定头再按长度循环收完整帧的流式解析器；没有在该函数里显式检查起始 02，而且是**先复制载荷、后验 BCC**。移植应先验证再交付数据，并用实际收到的字节数做所有边界检查。

Linux 的健康查询、状态和图像响应共用接收器：检查起始 02、L 边界、完整包 BCC、STATUS=04、预期数据长度及包外字节数。设备拒绝也先验 BCC；健康值不符或未知采集状态均报错。单字节状态接受逻辑 6 字节或带一个包外字节的 7 字节；图像在协议层接受逻辑 12165 或带一个包外字节的 12166 字节。普通图像交付后端时另行检查 12166 字节保存契约，缺少尾字节返回格式不支持，不补造数据，也不触发设备重同步；扩展图像完整消费后丢弃。分块共用总截止时间，具体边界见[协议文档](protocol.md)。

### 4.3 设备状态字与主机错误码不要混用

`M:3648` 的文本表：

| 设备 STATUS | 含义 |
| --- | --- |
| 04 | 命令成功，**不是手指按下标志，也不是图像类型** |
| 15 | 参数错误 |
| 80 | 设备报告超时 |
| A4 | 主密钥无效 |
| B5 | 命令及主密钥无效 |
| E0 | 命令无效 |
| E1 | 底层传输错误 |

这证明主机认识这些值，不证明 FT9362 固件会产生所有值。另有主机 `0xC00000A3` 未准备好、`0x80000011` 忙、`0xC0000120` 取消、WDF 传输错误等。不能把一个 NTSTATUS/HRESULT 的低字节作为设备状态。

| 扩展传感器数据 | `02 00 03 82 76 01 F6` | GetMoreData 请求 2×A×B 字节 | M:758C、B018 |
| SFR 1B | `02 00 02 84 1B 9D` | 1 字节，FPUID 输出第一个字节 | M:76BC、AD04 |
| SFR 1C | `02 00 02 84 1C 9A` | 1 字节，FPUID 输出第二个字节 | M:76BC、AD04 |

`FPUID` 在本样本中实际是两个 SFR 字节，不应凭名字当作已经证明全球唯一的传感器序列号。SCUID 与 FPUID 是两个不同接口。

### 5.2 参数化操作与模式写入

| 命令 | 参数布局 | 响应 / 使用方式 |
| --- | --- | --- |
| 80 | `index count`，均为 1 字节 | 直接读应用信息；不是已经确认的物理寄存器映射 |
| 89 | `index count` | 间接读应用信息，见 M:7334 |
| 87 | `index 01 value` | 写一个信息字节，消费无数据 ACK，见 M:7988 |
| 82 | 自定义参数序列 | 多用途通道；不能将 82 统一命名为 WAKE |
| 84 | `address` | 读取 1 字节 SFR |
| 37 | 调用方提供的 GPIO 参数 | 防误触调用为 `01 01 enable`，见 M:6320、6FAC |
| 32 | `mode` | 切换 bootloader；1 进入、0 退出，读 ACK 后等待 300 ms，见 M:77E4 |
| 33 | 升级子类型、序号、块数据 | 见第 10 节，不能用于普通采集 |

已核对的具体写包：

| 场景 | 完整包 |
| --- | --- |
| 应用唤醒 | `02 00 03 82 01 00 80` |
| WriteInfo(01,01) | `02 00 04 87 01 01 01 82` |
| WriteInfo(BB,BB) | `02 00 04 87 BB 01 BB 82` |
| 扫描模式 WriteInfo(6C,6C) | `02 00 04 87 6C 01 6C 82` |
| 手势模式 WriteInfo(40,40) | `02 00 04 87 40 01 40 82` |
| 深睡 WriteInfo(73,73) | `02 00 04 87 73 01 73 82` |
| 防误触 enable=0 | `02 00 04 37 01 01 00 33` |
| 防误触 enable=1 | `02 00 04 37 01 01 01 32` |
| 进入 bootloader | `02 00 02 32 01 31` |
| 退出 bootloader | `02 00 02 32 00 30` |

以上 `WriteInfo` 的**索引和值真的相同**，不能将相邻指令中的对象偏移 A6/A7/C4/C5/D6/FA 当作发到设备的索引。

`ff_device_set_ec_control`（M:3CE0）把高层 mode 转成自定义参数，第二字节固定 01：

| mode | 82 的参数 | 完整包 |
| ---: | --- | --- |
| 0 | EF 01 | `02 00 03 82 EF 01 6F` |
| 1 | EE 01 | `02 00 03 82 EE 01 6E` |
| 2 | 78 01 | `02 00 03 82 78 01 F8` |
| 3 | 72 01 | `02 00 03 82 72 01 F2` |
| 4 | F3 01 | `02 00 03 82 F3 01 73` |
| 5 | F4 01 | `02 00 03 82 F4 01 74` |

名称只说明作者将其归为 EC 控制，不能从数字反推“断电”“复位 GPIO”等电气语义。发送失败后有 USB 恢复调用。

另外存在**未封包的单字节 `00` OUT**，用于桥接唤醒及心跳前导；它不是长度为零的普通协议包。

## 6. 初始化、设备状态与正常采集

### 6.1 主初始化和恢复初始化是两条路径

硬件准备入口 `M:23F0` 建立 USB/协议对象、事件和线程所需资源，执行平台相关 ACPI/EC 准备，唤醒桥接，再进入 `M:39B4`：

```text
获取控制器版本：30
按版本字符串检查是否需要切换 bootloader / 下载嵌入固件
  若要重枚举：终止本轮准备，等待设备重新进入准备流程
将加密标志初始化为 0，再读应用信息 07
读应用信息 03、04，记录 A、B、P=A×B
查询应用状态：80 01 02
  按状态分支检查参数、进入 sensor 模式或继续准备
```

需要保留的实现细节：首次查询 07 的失败没有在这里严格上报，初值 0 会留下“不解密”的可能；第一次参数检查的结果也不是唯一决定准备成功的结果，后面还有检查。移植应明确区分“探测失败”与“设备声明禁用”，不能照抄这种降级。

`ff_sc_check_parameters`（M:7BFC）先用索引 03/04 读取两个字节，拒绝零尺寸，保存乘积；它不是 FT9362 型号鉴定函数。40×152 判断发生在图像处理处。

另一条 `ff_device_init`（M:38D8）→`ff_sc_fp_chip_init`（M:8448）：

```text
应用层唤醒
查询尺寸
WriteInfo(01,01) → ACK
WriteInfo(BB,BB) → ACK
config_device_mode(0)：sensor 模式
```

该路径出现在设备恢复逻辑中，不能把这两个写入描述为已证明每次正常 open 都执行。

`ff_sc_check_health`（M:7BAC）**只把输出清零并返回成功**，无 USB 自检；`on_device_died`（M:3D9C）含重初始化与至多追加 5 轮恢复逻辑，但依赖此占位健康检查的故障分支不能当作常态实测。

Linux open claim 接口并标记待同步，close 清理主机缓存并 release 接口。首次采集动作执行排空及桥接、应用、尺寸和扩展状态检查，不执行上述初始化写入，关闭时也不发送休眠命令。libfprint 的设备生命周期管理与这些健康查询均不等于完成了芯片初始化。

### 6.2 普通采集线程

证据 `M:E250`：

1. 检查工作、显示、暂停、直接采集等主机标志，普通路径并非后台无限无条件读指纹。
2. 有 pending capture 时持有阻止空闲的状态；相关分支先等待 10 ms，再等待 50 ms。
3. 普通检测阶段执行 `80 02 01`；返回非零映射为“有手指”，进入读图阶段；否则等 30 ms。
4. 直接采集标志可以跳过上述检测阶段。
5. `GetImage` 读取 81、按条件解密、预处理，写入最多 10000 字节的线程图像缓冲。
6. 成功后组装 WBDI 输出、通知等待方，完成该次工作。

**错误差异：** 普通线程对手指查询结果只判断是否等于 1，负错误也会走等待分支。图像读取遇到 `0xC00000A3` 会尝试驱动初始化，成功后返回检测阶段；其他图像错误清主机标志、记录日志并回到检测。不能概括成“Windows 每个 USB 错误立即结束 API 调用”。Linux 则明确使当前 action 失败。

### 6.3 Linux 的普通 / 扩展串行采集

```text
待同步时：有界排空 → 桥接 / 应用 / 尺寸检查 → 扩展查询
已同步时：直接进入扩展查询

扩展查询 → 06 → 等待 50 ms → 扩展查询
        → 05 → 普通查询 → 01 → 普通取图 → 协议及保存格式校验 → C++ 后端
                       → 00 → 扩展取图并校验消费 → 复查普通状态
复查普通状态 → 01 → 普通取图
            → 00 → 等待 50 ms → 扩展查询
```

没有硬件就绪等待总超时；调用方可取消。所有健康和采集命令共用接收与校验，超时参数见第 3 节；完整状态图、同步标记的清除条件及所有权约束见[开发指南](development.md#驱动生命周期)。扩展图像不交付后端，扩展或普通状态的未知值报协议错误。

成功路径在 SSM 完成回调中先检查普通帧保存契约，再同步调用后端；后端输入在调用期间借用响应缓存。复制输出后清理主机缓存，再完成 libfprint 动作。协议完整后的格式或后端错误不改变设备同步状态。用户取消等待当前命令事务结束或失败，轮询等待可直接取消；通信错误后的排空与重同步见第 9.4 节。

### 6.4 Windows 的额外图像获取入口

- **OnScanImage（M:BC24）**：拒绝与 pending 普通 capture 冲突；唤醒桥接；进入设备模式 6；每轮等 10 ms 后查询应用状态，计数初值 6，循环结构最多执行 7 次查询；就绪后通过 GetImage 返回 P 字节灰度图。它不是普通采集每帧必经的步骤。
- **OnGetMoreData（M:B018）**：先 `82 73 01`；只有返回值 05 才继续 `82 76 01` 获取 2P 数据，随后采用同样的条件 AES 和尺寸预处理，输出 P 字节。不满足状态时走值 `0xFF` 的结果路径。不能把此状态值 05 混入普通 `80 02 01` 判断。

Linux 已将 05 条件下的扩展读取纳入刷新流程，完整消费后仅向后端交付普通图像；未复制模式 6、AES 或预处理。

扩展响应长度证据：`M:B1B3` 将 A×B 加倍后调用 `M:758C`，后者在 `M:7646` 将该载荷容量交给读取封装；共享响应层 `M:DEB2`、`M:DEB7` 构造的是 D+5。因此 40×152 对应 D=12160、逻辑包 12165，不是 12166。底层对齐后的 USB 容量也不等于实收长度。Windows 不能证明扩展响应必须包含额外尾字节；`FT9362-RAW-v1` 是 Linux 保存契约，不是 Windows 协议名称。Linux 对普通帧保留此契约，扩展响应只按协议边界校验。

这些接口提供额外采集通道。[本机实验](device-capability.md)已验证 GetMoreData 的 05 条件与扩展图像读取，并发现其参与推进普通帧更新；SCAN_IMAGE 模式尚未验证，两种取图命令对应的具体物理缓冲关系仍不明确。

## 7. 图像数据与 Windows 预处理

### 7.1 三种长度及原始图像布局

对 A=40、B=152：

```text
P = A×B = 6080 个采样
D = 2P = 12160 = 0x2F80 字节载荷
L = D+1 = 12161 = 0x2F81
协议逻辑响应 = D+5 = 12165 字节
Linux 保存格式 = 12166 字节
```

| 偏移（从完整响应开始） | 字节数 | 含义 |
| ---: | ---: | --- |
| 0 | 1 | 起始 02 |
| 1 | 2 | 大端长度 2F 81 |
| 3 | 1 | 成功状态 04 |
| 4 | 12160 | 图像载荷；需要时先整体解密 |
| 12164 | 1 | BCC |
| 12165 | 1 | Linux 既有格式中的额外字节，Windows 协议解析不消费；来源未定 |

40×152 专用路径按 `uint16_le` 读取连续采样，行步长 40 个采样，共 152 行。原始采样存储单元是 16 位，**不证明 ADC 有 16 位有效精度**。设备安装朝向也未因此确定。

Windows 把 USB 头、STATUS、BCC 去掉后才交给图像处理。Linux 后端拿到完整帧。Python 的图像视图从偏移 4 取值，百分位拉伸、反色及显示朝向只用于预览，原始保存不变。

单字节状态响应逻辑长度为 6 字节，Linux 接受 6 或 7 字节；普通和扩展图像在协议层均接受 12165 或 12166，普通图像交付后端时另行要求完整 12166 字节保存格式。协议长度、USB `actual_length` 和额外字节分别处理，不将包外字节作为像素或 BCC。

### 7.2 AES-128-CBC：已模拟核对

证据：读取开关 `M:680C`，调用 `M:6661` 附近，计算入口 `M:1614`。

| 项目 | 恢复值 |
| --- | --- |
| 启用条件 | 应用信息索引 07 的值恰好等于 01 |
| 输入 | 协议层提取的 2P 字节图像载荷 |
| 算法 | AES-128-CBC |
| key | `eb4aa01368d846470d2baee39d020fdf` |
| IV | `d5aa36a54b7b1835f237d3f0c54549bb` |
| key / IV 数据 RVA | M:1E000 / M:1E010 |
| wrapper mode | 0 解密，1 加密；GetImage 用 0，输入输出同地址 |
| 分组 | 16 字节；12160 恰好为 760 块，无需增加 padding |

使用隔离 x86-64 模拟器执行原 wrapper，并与独立 AES-CBC 库交叉比较：64 字节和 12160 字节输入，正逆两个模式均一致。没有加载驱动到 Windows，也没有执行 USB、安装或固件更新逻辑。

不依赖原 DLL 的回归向量：

```text
明文：00 01 02 ... 3E 3F（依次递增，共 64 字节）
key / IV：见上表
密文：
4fce67c0072b2f1eb8be110225776f72
```

该固定 key/IV 来自共享主机代码，不是从用户指纹提取的模板。不能因此认定本机原始帧已加密；本机 07 响应仍未知。解密也不意味着获得了设备认证、签名验证或防重放机制，本文没有找到这些机制在此图像路径中的证据。

### 7.3 40×152 专用预处理的阶段与参数

证据 `M:4958`，辅助函数 `M:46D4`、`M:4770`。调用实参为 `(raw16, gray8, height=152, width=40)`。这是主机图像变换，不是身份匹配。

以下描述覆盖已核对的计算阶段；它还不是逐像素等价移植已通过测试的声明。整数除法向零截断、float32 运算和边界规则会影响复刻结果。

1. **全局归一化与反向映射。** 遍历 P 个无符号 16 位采样，最大值初值 0，最小值初值 4096；相等时提前跳转清理。设取得的 `lo`、`hi`，`range=hi-lo`，构造临时 8 位图像和原位 16 位归一化值：

   ```text
   q8[i] = uint8(trunc((lo - raw[i]) * 255 / range) - 1)
   q16[i] = uint16(1024 + trunc((lo - raw[i]) * 1024 / range))
   ```

   最小值以 4096 为初值是实际实现细节；如果输入全大于 4096，它不是通常意义上的真实最小值。不能把该常量当成已证明的 ADC 满量程。

2. **分区统计。** 将 152 行分成四个 38 行区域，求 q16 均值。取四区均值最小值 m，再在小于 `m+256` 的均值中选较大的参考值 r。阈值为 `r<200 ? r+200 : 2*r`。

3. **局部掩码。** 初始化 P 字节掩码为 0。以 8×8 区域求 q16 均值，超过上述阈值则在对应中心处写 FF；循环采用 `y<height-8`、`x<width-8`，中心偏移为 `(4,4)`。

4. **掩码膨胀。** 先水平 17 点最大值，再垂直 17 点最大值，等价于半径 8 的方形膨胀。边界为不重复端点的反射：例如 -1→1、width→width-2；不能替换成补零或复制边界后声称完全等价。

5. **梯度与掩码可信度。** 对 q8 内部像素计算 Sobel 型水平/垂直梯度，形成幅值图。平方根使用 float32 的快速倒平方根近似：初始位模式 `0x5F375A86 - (bits(value)>>1)`，一次 `y *= 1.5 - 0.5*value*y*y`，再取 `trunc(1/y)`。边缘幅值保持初始化的 0。

   分别统计掩码内外梯度均值，分母均为计数+1。设掩码内比例 c、内均值 gin、外均值 gout，选择掩码外范围的条件为：

   ```text
   c < 0.12:  gin <= gout + 90
   c >= 0.12: gin <= 150 且 gin <= gout + 40
               且 !(c > 0.18 且 gin > gout + 30)
   ```

6. **掩码外直方图限幅。** 从掩码为 0 的 q16 统计范围、构造 400 桶直方图。桶号 `clamp(trunc((q16-lo)*399/(hi-lo)),0,399)`；尾部计数阈值来自样本数×参数/1000，本调用参数=1。函数双向累计并按命中桶内计数位置调整桶号，换回数值时使用 `(bucket*range+200)/399+lo`。主调用使用上限结果限制外部最大值；不是 Python 预览使用的 5%/95% 拉伸。

7. **最终 8 位输出。** 按第 5 步条件选择掩码外范围或全局 q16 范围，设下限 a、上限 b：

   ```text
   t = clamp(trunc((q16[i]-a)*250/(b-a+1)), 0, 250)
   gray[i] = 255-t
   若 mask[i] != 0 且 gray[i] == 250，则改为 254
   ```

8. 清理临时缓冲。末尾调用 `M:DCB0`，该函数只有 `return true` 的机器码，**没有额外旋转、增强或质量检测**。

异常路径也不能忽略：均匀输入或分配失败可提前退出，未看到对所有提前路径保证写满输出的处理；部分临时内存在检查空指针之前已有写入。不要照搬这些内存处理缺陷。直方图边界、退化图像及 float32 舍入需要独立复现测试，目前不宣称可与 Windows 所有输入逐像素一致。

其他尺寸调用 `M:54C4`，不属于此处的 40×152 专用处理路径。

### 7.4 亮度检查与真正的样本拒绝

主 DLL `M:6788` 使用 `sum(gray)/(P+1)`：

| 均值 | 分类值 |
| --- | ---: |
| <50 | 2 |
| >200 | 1 |
| 60..180 | 0 |
| 50..59 或 181..200 | 4 |

GetImage 根据该结果记日志，但并不以此拒绝图像。上层封包 `M:1B58` 另算 `sum(gray)/P`；不在 `[40,200]` 时调用 EC-control mode 3，即 `82 72 01`，等待 100 ms，随后仍继续封包。

引擎 `E:10F640` 的 AcceptSampleData 才有另外的质量拒绝边界：先确认格式 owner=001B、type=0401、像素深度=8、压缩标志=0；取图像调用质量接口。质量计算失败返回 `0x8009800C`；质量结果中的拒绝字段非零时，返回 `0x80098008`、RejectDetail=7。这与主 DLL 的亮度日志是两层不同机制。

质量接口还输出 coverage、quality、humidity、over-exposure coverage、acquired-info（E:10D2D0）。引擎包含增强、噪声过滤、非手指/假手指检测等配置入口；仅有入口不证明在当前配置下启用。其完整数值算法和实际启用组合尚未恢复，不能用“忽略匹配算法”来把这些采集质量差异隐去。

## 8. Windows 上层数据与私有接口

### 8.1 WBDI 请求约束

普通捕获 `M:1D7C`：一次只允许一个 pending request，重复请求返回 `0x8009800B`。输入最少 0x20 字节；格式 owner 位于 +6，要求 001B，type 位于 +8，要求 0401。purpose 在 +4，接受 01/02/04/08/10/80；data type 在 +1C，接受 01/02/04/08/20/40/80。

purpose、data type、format 错误分别返回 `0x8009800E`、`0x8009800D`、`0x8009800C`。输出所需长度 `P+0x9C`，目标设备为 **6236 字节**；小缓冲查询路径可以在至少 4 字节的输出中返回所需大小，不能将它视为成功采集了一帧。

Linux 不存在这个 WBDI 二进制输入结构；由 libfprint action 类型决定 enroll/verify/identify。

### 8.2 输出包布局

证据 `M:1B58`。下列为**Windows 输出缓冲绝对偏移和本机整数写入值**，不是将某国际图像标准的结构体直接 memcpy 出来的建议。多字节整数以此 x86-64 样本的小端内存表示。

### 8.4 引擎 / 存储契约（不展开匹配）

引擎 attach 用 SensorSize 私有请求取 A/B，分配图像上下文；AcceptSampleData 消费 8 位未压缩图像并进行质量检查；Activate/Deactivate 通过 APP_LOCK/APP_UNLOCK 与主 DLL 协调。引擎自己的 NotifyPowerChange（E:111780）只校验若干通知值并返回，不执行 USB 电源控制。

录入接口有建立、更新、提交和丢弃阶段；QueryExtendedInfo 向系统提供一般样本数及中心、上下左右边缘的采集引导数量。INF 设置 Center=8，四边各=2，但不能简单把这些相加当作每次录入必需按压次数；还取决于引擎返回值与上层流程。

提交时通过厂商 template_export 取得长度与内容，再交系统 StorageAdapter；不存在本工程当前这种“把完整 USB 帧直接作为存储模板”的等价关系。模板内部结构、特征提取和身份匹配不在本文复刻范围。未找到主 DLL 提供设备内模板枚举/删除/匹配命令的证据；这也不等于证明硬件绝对不具备任何未被此驱动使用的功能。

## 9. 电源、显示状态、取消与恢复

### 9.1 两层唤醒

桥接唤醒 `M:977C`：

```text
查询 34；55 AA → ready
否则最多 10 轮：
  raw OUT 00
  等待 1 ms
  查询 34
  ready 则结束
```

该函数只对 mode=0 有实质实现；其他值日志后返回，不能推断有对称的“桥接深睡”命令。

应用唤醒 `M:8044` 的 mode=0：

```text
查询 80 01 02；A5 5A → ready
否则最多 10 轮：
  82 01 00 → 消费 ACK → 等待 5 ms
  82 01 00 → 消费 ACK → 等待 10 ms
  查询 80 01 02
```

代码对最终“忙”和负错误的处理并不处处对称；不能假设所有失败最后都被归为同一超时。移植应保留显式传输/协议/就绪错误，不复制被忽略的错误。

### 9.2 休眠与设备模式

普通休眠 `M:8688`：

1. 两次 WriteInfo(01,01)，各消费 ACK。
2. 每 3 ms 查询应用状态，最多 50 次，等待 ready。
3. 间接读 `89 index 01`。index 取可变全局参数区 +C3 的当前字节；读回数据也覆盖该字节，**没有证据可将它固定命名为某硬件寄存器**。
4. 再查询应用状态，要求返回“非就绪”的规范值 1，否则报错。

调用者 mode=1 对这个完整过程最多追加 3 次重试。未确认中间间接读取是读清除、中断消费还是其他机制。

| 应用电源 mode | 实际动作 |
| ---: | --- |
| 0 | 上述应用唤醒 |
| 1 | 上述普通休眠初始化 |
| 2 | WriteInfo(01,01)；相邻主机字段 FA 被置 1，但 FA 不是命令索引 |
| 3 | 先 mode 0，再 WriteInfo(73,73)，日志称 DEEP_SLEEP |
| 4、5 | 无实质动作后返回 |
| 其他 | unknown 日志后返回，不能算硬件支持 |

设备模式入口 `M:7DD4` 与电源 mode 是不同枚举：

| 设备 mode | 实际动作 |
| ---: | --- |
| 0，以及多个默认分支 | 日志 SENSOR；先应用唤醒，再普通休眠初始化 |
| 1 | 日志 POA；应用唤醒 |
| 6 | 日志 SCAN_IMAGE；WriteInfo(6C,6C) |
| 7 | 日志 GESTURE；应用唤醒，再 WriteInfo(40,40) |

“GESTURE”只确认命令路径存在。没有恢复 FT9362 手势事件格式、方向上报或 Linux 输入事件，不能把它写成已经确认的 FT9362 导航能力。

### 9.3 WDF、显示与防误触

INF：SystemWakeEnabled=1、DeviceIdleEnabled=1、UserSetDeviceIdleEnabled=1、DefaultIdleState=1、DefaultIdleTimeout=5000、WinUsbPowerPolicyOwnershipDisabled=1、WdfDirectedPowerTransitionEnable=1。

代码 `M:3308` 将系统能力判断结果记录为 modern/legacy standby 标志；`M:F5C4` 据此选择 modern 分支 5120 ms、legacy 分支 5000 ms idle 超时，并配置系统唤醒。运行时读取 remote-wake 等 traits；安装配置表示策略请求，不保证硬件总能唤醒主机。

主 DLL 注册电源通知（M:9F38），显示通知（M:9C60）区分 off/on/dim：off 记录时间并改变多个主机标志；on 恢复显示标志及转换标志；dim 只记日志。显示 callback 本身没有直接发 USB，后续工作线程及 D0 流程使用这些标志。

防误触 `M:6FAC` 还要求 app 标志（对象 +69）非零；该标志为零或显示关闭时直接退出，满足条件才通过 `37 01 01 enable` 操作 GPIO。具体 GPIO 对应电源键还是传感器中断，不能由日志确定。

创建路径 `M:2910` 注册的 PnP / 电源回调如下。入口归属按回调结构字段核对，而非根据函数内的动作推测；字段布局和 API 表索引参照微软公开的 [UMDF 头文件](https://github.com/microsoft/Windows-Driver-Frameworks/blob/main/src/publicinc/wdf/umdf/2.27/wdfdevice.h)和[函数表](https://github.com/microsoft/Windows-Driver-Frameworks/blob/main/src/publicinc/wdf/umdf/2.27/wdffuncenum.h)。

| 回调 | RVA | 已确认的动作 |
| --- | --- | --- |
| EvtDeviceD0Entry | M:2CC0 | 按来源电源状态及显示标志，条件执行 USB reset、桥接唤醒、应用状态检查、重新初始化、sensor 模式及 EC-control |
| EvtDeviceD0Exit | M:3000 | 清运行标志，调用 WdfDeviceGetSystemPowerAction；未发现直接 USB 命令 |
| EvtDeviceSelfManagedIoInit / Restart | M:3070 | 取得队列及设备上下文，设置运行标志 |
| EvtDeviceSelfManagedIoSuspend | M:3100 | 条件销毁关联工作对象，清运行标志，按请求及 app 状态决定 EC-control mode 2（82 78 01），并调用关闭防误触的入口；后者仍受 app / 显示条件限制 |
| EvtDeviceSelfManagedIoCleanup | M:3060 | 清运行标志 |
| EvtDeviceReleaseHardware | M:2860 | 销毁关联工作对象和 timer 对象，条件注销通知，经 M:EE90 删除 WDF USB 对象，再经 M:32A0 设置并关闭事件句柄、删除临界区 |

自管理 I/O 的 suspend 是设备进入低功耗前的生命周期回调，不是应用文件关闭回调，见微软[自管理 I/O 说明](https://learn.microsoft.com/en-us/windows-hardware/drivers/wdf/using-self-managed-i-o)。上述退出路径未发现普通休眠入口 M:8688 或应用电源 mode 3 的直接调用。EC-control mode 2 也不是应用电源 mode 2。普通休眠可经 sensor 模式在初始化及条件 D0 entry 路径调用；不能由此推断关闭应用句柄会发送休眠或 deep-sleep 命令。

### 9.4 心跳、取消及拔出

心跳 `M:6D74` 每轮 raw OUT 00→等 2 ms→35→读两字节，期望 55 BB，最多 10 轮；有 WDF timer callback（M:E700）串行调用并记录失败。进一步检查构造点 `M:24E1`：传入的 timer period 为 **0**，不是一个已配置的周期心跳。保存 timer 指针的全局位置只找到准备和释放路径的直接引用，没有找到对应启动调用。因此应记录为“存在心跳操作及 timer callback，未证实实际运行”，不能把 10 轮当作定时周期，也不能据此要求 Linux 常驻轮询 35。

Windows 采集路径 `M:1E3B` 将 `M:1910` 注册为请求取消回调。该回调停止相关工作对象、取得互斥锁和临界区，必要时调用 WdfDeviceResumeIdle 释放 idle 引用，若是当前 pending request 则清空引用与主机“中断”标志，以 `0xC0000120` 完成请求。`clean_level_interrupt`、`enable_Interrupt`、`disable_Interrupt`（M:3824/3860/389C）是主机状态操作，不能命名成已经找到硬件 ACK/STOP。

主 DLL 的设备创建路径及函数表调用检索未发现 WdfDeviceInitSetFileObjectConfig，也未找到自定义 EvtFileCleanup / EvtFileClose 注册。微软规定这类回调通过该 API 注册，且[文件关闭回调](https://learn.microsoft.com/en-us/windows-hardware/drivers/ddi/wdfdevice/nc-wdfdevice-evt_wdf_file_close)发生在未完成请求已结束或取消之后。因此当前静态证据指向框架处理文件生命周期、驱动通过请求取消回调处理在途采集，而不是每次关闭应用句柄都执行 ReleaseHardware。M:32A0 中的 CloseHandle 关闭的是内部事件句柄，不是应用持有的指纹设备句柄。未在 Windows 上跟踪实际关闭时序，不能将这些静态入口串成已经实测的完整调用链，也不能仅凭 Linux close 未发休眠命令就认定资源清理不完整。

拔出通知 `M:31F0` 改变拔出/运行状态，并使用 `suprice_removed` 注册表标记；prepare 路径会检查该标记。USB ErrorRecover（M:EEC0）的 reset 与这些主机标志是不同层次。

Linux 将一次 OUT 与完整响应接收组织为命令事务。action 取消在事务边界生效，传输使用独立的有界超时；完整响应后的正常取消不强制重同步。通信错误则保留待同步状态，下一动作有界排空并检查桥接、应用、尺寸及扩展状态。驱动没有主动 reset、clear-halt、桥接唤醒或加密状态恢复。设备重枚举由 libfprint/GUsb 生命周期处理，驱动不把旧对象改绑到新地址。状态与所有权约束见[开发指南](development.md#驱动生命周期)，实机证据与局限见[设备能力](device-capability.md)。

证据 `M:88C0`，版本比较 `M:7AB8`。按控制器版本字符串选择分支，之后再区分 APP / IAP。固件选择依据命令 `30` 的响应及运行状态；本机查询值见下表，版本相同不构成刷写兼容性证明。

| 控制器字符串条件 | 内置 payload RVA / 长度 | 比较用目标字符串 | 归属说明 |
| --- | --- | --- | --- |
| STM | 1E110 / 31676 | RTS_USB_APP_202110271500 | payload 内出现 fw9362 函数名；仍需本机版本匹配，STM 条件与 RTS 字符串不得擅自“纠正” |
| HC32 | 25CD0 / 57204 | FT9769_APP_HC32_USB_ENC_SV0.1_202107130909 | 明确带 FT9769；不作为 FT9362 固件 |
| HT32 | 3B900 / 54472 | FT9769_APP_HT32_USB_DEC_SV0.1_4324_PowerKey | [本机查询](device-capability.md)返回相同版本；不能仅凭字符串认定刷写兼容 |
| ES210 | 33C50 / 31909 | APP_V0203_ES210_20211110 | 不能仅由这个字符串归属 FT9362 |

| payload RVA | SHA-256 | CRC32 |
| --- | --- | --- |
| 1E110 | `15386a4c44fc2f0bf075adebeb333a67f5d532f5dc1da1f99e3401bf9cad0cb8` | C562284E |
| 25CD0 | `767604e7853b9874f444a29d69a78c9725faa5d6c771e326b1d6fbc2433dfccd` | EB986E7B |
| 3B900 | `6e68bd2b3a832b62a2b103c789db8221a47d91969282533e3521a7caef0b25c2` | CFE7AE46 |
| 33C50 | `ed1e94055421ec51e346f24e1fdbaf15a7d45b7e5fa53695fa75dbb79a99153c` | 2A7E2BDC |

上述 payload 嵌入于归档的主 DLL；表中 RVA、长度与摘要用于定位和核验，仓库没有独立提取的固件镜像文件。

升级主机协议：

1. APP 状态且版本判断要求更新：发送 32 mode=1；该 helper 读 ACK 后自身等待 300 ms，调用方再等 100 ms，置重枚举标志并以特殊结果结束准备流程。
2. IAP 状态：计算固件 CRC32；多项式 `EDB88320`、初值 FFFFFFFF、最后取反，按字节顺序处理（M:9974）。
3. 首包 135 字节：`02 00 83 33 01 00 [128 字节元数据] BCC`。元数据起始 64 字节为目标版本区，之后 4 字节为长度的大端布局、4 字节为大端 CRC32；其余区域需要保持样本的初始化语义，不应臆造签名字段。发送失败最多追加 3 次重试，然后读 ACK，等 15 ms。
4. 完整数据块 1024 字节：`02 04 03 33 02 seq [1024 数据] BCC`，总长 1031，seq 从 1 递增。写后等 100 ms，再读 ACK，再等 15 ms。
5. 最后块使用 subtype=04，长度仍为 1024 数据字节；复制余数，尾部补零，包仍为 1031 字节。写后等 200 ms，读 ACK，再等 15 ms。
6. 32 mode=0 退出，helper 等 300 ms，调用方额外等 100 ms，置重新准备/重枚举标志。出错路径也尝试退出 bootloader。

该机制不是证实“FT9362 每次启动都需要下载传感器微码”。控制器固件与传感器初始化不是同一概念；设备在 APP 且版本合适时不应进入刷写流程。本文也没有恢复每个嵌入固件内部的 MCU/传感器控制程序。

Linux 当前没有升级功能。移植正常采集不需要首先复制刷写能力；读版本、明确桥接归属与准备恢复机制应先完成。

## 11. 平台集成、配置及辅助服务

### 11.1 ACPI 与 EC

主 DLL 有 ACPI `_DSM` 构造与执行（M:3EF4、44C4、456C），不是单纯的 USB 驱动。构造的 UUID 为 `EA9A9C7B-7BAB-468C-84FA-A9A59F8AD1CB`，来自 16 字节 GUID 数据。参数构造可见 revision/function 参数、请求对象、同步发送与输出签名检查。

尚未得到目标主机 ACPI 表、DSM function 的电气语义及返回契约。因此不能仅凭驱动包将这段平台行为替换成某个 Linux GPIO、电源资源或通用 USB reset。`ff_device_set_ec_control` 的 USB 82 子命令也不能与 ACPI `_DSM` 当作同一个调用。

| 主机进程 | ProcessSharingDisabled；允许直接硬件访问、Impersonation、未知/空 FileObject | 本工程不创建 Windows 式驱动宿主 |
| 访问控制 | Exclusive=1；DACL 给管理员和 LocalSystem GenericAll | USB 节点权限与 udev；构建不等于规则已部署 |
| 生物识别模式 | SensorMode=1（basic），SystemSensor=1 | FpDevice，PRESS，1 次 enroll stage，VERIFY/IDENTIFY |
| 插件 | 系统 SensorAdapter、厂商 EngineAdapter、系统 StorageAdapter | C 驱动 + 独立 C ABI/C++ 后端 |
| 存储 | DatabaseID=`1000F3B5-9412-490e-97BA-4AA5A1A171AE`，Format=`CDAE92F1-5B32-4a91-94A8-56ACA204B3B9`，AutoCreate/AutoName | FpPrint 序列化，采集工具可另存 SQLite 原帧 |
| 日志 | WPP/调试输出、focalFp EventLog，独立事件资源 DLL | libfprint 日志与工具输出 |
| 安全生物识别配置 | INF 写 SecureBiometrics Enabled=0；SGX 文件项被注释 | 不能据包中字符串声称两端已有硬件可信执行方案 |

INF 中非匹配相关默认值包括 AppLockEnable=1、NonFingerDetect=0、CheckEnable=0、ValidEreaScore=45、ValidEreaCenterRate=200、QualityScore=20、CondScore=15。注册表默认值不等于所有值都在 0752 的每个路径中被使用，尤其不能把“存在假手指检测配置入口”写成“已启用活体检测”。

C652 的 location/shape/powerbutton/startbutton 注册表行在 INF 中是**注释**，不是有效配置。事件资源 DLL 与 CAT 文件不是 USB 协议实现。

### 11.3 守护服务的型号排除

INF 为两个 PID 的共同安装节添加自动启动的 `focalFpSrvcDeamon.exe`。服务具有生物识别设备枚举、问题状态检查、设备重新枚举、显示通知相关代码。

但 `S:22FC` 获取设备实例 ID 后明确查找 **`VID_2808&PID_C652`**，再判断问题状态并触发重启。这条“故障设备自动重启”不能归到 PID_0752。服务中还有主设备树重枚举调用（S:1F30、2490）；全局重新枚举可能影响系统设备发现，却不等于该服务为 0752 实现了专用恢复协议。

Linux 不必为了“功能齐全”复制一个常驻 Windows 服务；应先实现本目标设备的 USB 生命周期与恢复，再判断是否确有平台补偿需求。

## 12. 不应照搬的 Windows 行为与空实现

| 行为 | 已核对事实 | 移植建议 |
| --- | --- | --- |
| check_health | 无 USB，输出清零、成功返回 | 不新增虚假的硬件健康检查 |
| Calibrate / Reset IOCTL | 主机格式应答，无对应芯片操作 | 不因接口名假定校准、硬件 reset 已存在 |
| clean/enable/disable interrupt | 改主机变量 | 不生成不存在的 USB 中断控制包 |
| 图像处理末尾 M:DCB0 | return true | 不新增一层没有行为的处理抽象 |
| engine NotifyPowerChange | 校验参数并返回 | 真正设备 PM 在主 DLL / WDF，不在此函数 |
| 成功短读 / 短写 | 底层缺少严格实际长度处理 | 保留并加强 Linux 已有边界检查 |
| 响应 BCC | 先复制再检查；错误 STATUS 分支绕过 BCC | 先校验，再交付载荷 |
| 初次信息查询失败 | 部分返回值被忽略 | 区分未知与禁用，禁止静默使用错误配置 |
| 普通轮询 USB 错误 | 可能继续轮询而非结束 | 采用明确的重试预算与恢复策略 |
| GetImage 读原始图失败 | 已分配的临时缓冲存在未经过正常 free 的返回分支 | 用一致的资源所有权与错误收尾 |
| 预处理退化输入 / OOM | 存在未写满输出、先写后检查空指针的路径 | 显式返回失败或定义稳定输出，不复刻缺陷 |
| 固件版本字符串不一致 | 比较目标和 payload 内自报版本不完全一致 | 原样记录并实测，不自行替换 |

Linux 已实现响应校验、运行时固定尺寸检查和错误后重同步，但仍使用固定保存格式，没有设备专用电源初始化或动态尺寸适配。重同步经过软件模拟验证，尚待当前驱动实机验收；有界排空及健康检查不能证明所有合法响应的新鲜性。

## 13. 移植顺序及验收依据

### 13.1 保持架构简单的实现顺序

1. **协议边界。** 健康和采集命令共用按实际长度校验的接收器，区分 status/data/trailer；后续新增命令沿用边界规则，仅在需要参数化请求时增加封包器。保留异步 FSM 和命令事务边界取消的所有权约束。
2. **只读探测。** 驱动已检查桥接/应用状态和固定尺寸；版本与 07 标志等额外查询按功能需要接入。只记录非指纹协议元数据；空 ACK 不作为有效标志值，未确定型号/固件分支时不自动升级。
3. **初始化与恢复。** 先实机验收已有的排空和健康检查，再依据明确的前置条件验证桥接唤醒、应用唤醒和 sensor 模式。区分冷启动、USB reset、resume 与采集取消，复用相同动作；查询成功不等于已经完成电源初始化。
4. **图像边界。** USB C 层输出经过协议验证的原始载荷及尺寸/加密元数据；独立 C++ 图像层可实现 AES、16→8 位处理和质量判定，保持无 GLib。不要让 C++ 处理 Windows IOCTL 或 libfprint 对象。
5. **电源。** 证明传感器模式转换后再对接 Linux suspend/resume/idle；保持取消可打断等待，保证每个 action 只完成一次。
6. **诊断接口。** 版本、UID、计数、原始透传与固件工具按实际需求单独实现。Windows 平台服务、ACPI、其他型号固件不自动移入核心驱动。

上述条目是扩展实现约束；当前实现范围见第 2 节，待验证能力见第 14 节。

### 13.2 无原 DLL 也能构造的协议测试

- 用第 4 节公式重建第 5 节全部命令并核对 XOR。
- 解析 5 字节 ACK、6 字节手指状态；拒绝短头、L=0、L 超出实际数据、坏 BCC、未知状态、零长度图像块。
- 12160 图像载荷应得到 L=2F81、逻辑长度 12165；分别测试没有额外字节、有一个额外字节、USB 对齐尾部和跨 transfer 分片，不能把尾部自动算进像素。
- AES 使用第 7 节独立向量；同时测 07=0、1、未知/查询失败，保证失败不被当成“明文”。
- 对图像处理测试均匀图、0/4095 边界、超过 4096 的值、8×8 阈值边界、反射边界、掩码 12%/18% 条件、空分区、OOM；逐像素 Windows 对照尚未完成。
- 取消覆盖写状态命令、读状态、轮询等待、写采集命令、读图、恢复等待；取消后再启动不得接收上次 action 的帧。
- 模拟成功短写、短读、超时、非零设备状态、重试导致的重复 ACK；恢复后重新确认尺寸/07，不沿用未知缓存。

当前 Linux 的模拟 USB/适配层回归已覆盖普通与扩展通道、协议校验、连续采集与残留响应，见[开发指南](development.md)。它们不是以上全部协议功能的验收，也不是实机电源/固件验证。
