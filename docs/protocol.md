# 协议与数据格式

目标为 FT9362，USB `2808:0752`。本文汇总当前 Linux 实现与原始帧证据；完整 Windows 命令、初始化和电源流程见 [Windows 移植参考](windows-reference.md)。静态分析结果不等同于本机硬件验证。

## 当前 USB 通信

| 项目 | 当前值 |
| --- | --- |
| USB 接口 | 0 |
| Bulk OUT / IN | `0x03` / `0x81` |
| 状态读取容量 / 最小接受长度 | 64 / 7 字节 |
| 命令写入与状态读取超时 | 1,000 ms |
| 每次图像读取超时 | 5,000 ms |
| 无手指后的轮询间隔 | 50 ms |
| 完整采集帧长度 | 12,166 字节 |

[驱动](../driver/focaltech-0752.c)只发送两种请求：

| 用途 | 完整命令 | 含义 |
| --- | --- | --- |
| 查询手指状态 | `02 00 03 80 02 01 80` | `80` 读取应用信息；从索引 `02` 读取 `01` 字节 |
| 读取图像 | `02 00 01 81 80` | `81` 为图像读取命令，无附加参数 |

命令中的 `81` 与 USB IN 端点地址相同，但二者分别属于协议与 USB 传输层。

早期根据固定命令提出的结构推测，已由 Windows 主机封包代码补充确认：

```text
02 | 内容长度（大端 uint16） | 命令及参数 | BCC
```

内容长度包含命令字与参数；BCC 为长度字段及全部内容逐字节 XOR，不含起始 `02`。状态查询内容为 `80 02 01`，长度 3；图像查询内容为 `81`，长度 1。详细命令条件见 [Windows 参考第 4–5 节](windows-reference.md)。

响应的内容区从状态码开始，`04` 表示命令成功。当前 Linux 对手指响应只检查最小长度、偏移 0 的 `02`、偏移 3 的 `04`，且只将偏移 4 的 `01` 视为有手指；不验证长度字段与 XOR。Windows 将非零状态值视为有手指，两者尚未统一。

Windows 的单字节状态响应逻辑长度为 6，而 Linux 最少接受 7；图像响应逻辑长度为 12,165，而当前 Linux 固定接收 12,166。逻辑包长度、USB 请求容量与实际传输长度必须分别处理，不能直接互换。

## 原始帧布局

以下来自 2026-10-10 一次录制中的 **55 个不同帧**，并结合 2026-10-11 Windows 静态分析。所有偏移从 0 开始，范围包含两端。

| 偏移 | 长度 | 解释与证据 |
| --- | ---: | --- |
| 0 | 1 | 固定 `02`，与 Windows 协议起始标记一致 |
| 1–2 | 2 | `2f 81`，大端值 12,161：状态字节加图像载荷长度 |
| 3 | 1 | `04`，命令成功状态 |
| 4–12163 | 12,160 | 6,080 个小端无符号 16 位采样值，按 40 列、152 行解释 |
| 12164 | 1 | 偏移 1–12163 的 XOR，55/55 帧匹配 |
| 12165 | 1 | 额外尾字节，含义未确认，原样保留 |

```python
import struct
from functools import reduce
from operator import xor

assert len(raw) == 12166
assert raw[:4] == bytes.fromhex("02 2f 81 04")
assert reduce(xor, raw[1:-2], 0) == raw[-2]
pixels = struct.unpack("<6080H", raw[4:-2])
rows = [pixels[y * 40:(y + 1) * 40] for y in range(152)]
```

该示例是对本批响应的离线校验，不是当前驱动的通用解析器。Windows 在运行时尺寸为 40 × 152 时选择专用图像处理，并以无符号 16 位读取采样值；这支持上述解释，不证明所有设备分支均采用同一格式。

图像读取可能按应用信息索引 `07` 的值启用 AES-128-CBC。当前 Linux 与 Python 均不解密。密钥、IV、条件及测试向量保留在 [Windows 参考](windows-reference.md)，不能无条件对所有原始帧解密。

## 图像布局的历史证据

统计基于偏移 4 的原始值，不使用拉伸或反色后的预览。

| 指标 | 结果 |
| --- | ---: |
| 40 列排列：相邻行 Pearson 相关性，逐帧取中位数 | 0.899 |
| 80 列排列：同一指标 | 0.636 |
| 40 列排列：行内相邻值绝对差中位数 | 72 |
| 每 40 个值的换行边界绝对差中位数 | 424 |
| 第 76、77 行间平均绝对差，跨帧取中位数 | 183.2 |
| 其他相邻行平均绝对差中位数 | 171.6 |
| 两个 40 × 76 半幅直接比较的相关性中位数 | 0.048 |

数据支持一张 40 × 152 图像，而非两张重复的 40 × 76 图像。旧的 80 × 76 排列会把相邻两行并列；偏移 6 解码还会漏掉首个采样值，并把尾部字节当作末尾像素。工具已移除这些旧布局。

本批值域为 **64–3,324**。334,400 个采样值中，334,387 个是 4 的倍数；其余 13 个均位于索引 1,677，即零基行 41、列 37。原因未确认，不应丢弃低两位。16 位是存储单位，不能据此认定 ADC 位深。

尾字节有 49 种取值（`03`–`ed`），没有逐帧递增规律，也不是前一校验字节的简单取反。对不同切片尝试的求和、XOR、取反、负和、字求和、Fletcher 与 CRC-8 候选均未匹配全部样本；这不能排除所有私有校验。该字节可能是填充或发送缓冲区残留，但没有确证。

55 帧首末接收时间相隔 **25.616 秒**，54 个间隔对应平均 **2.108 FPS**；间隔中位数 0.372792 秒，最短 0.175377 秒，最长 3.213282 秒。中位数的倒数约 2.682 FPS，不等于平均 FPS。这些是一次主机交付速率测量，不是硬件上限。

## 保存、显示与未知项

[frame.py](../tools/frame.py)将完整帧解码为 40 × 152 预览，采用 5–95% 分位对比度拉伸，可反色；保存的原始字节不变。FpPrint 内部为 `("FT9362-RAW-v1", 字节数组)`，GVariant 类型 `(say)`。该标签标识完整原始帧封装，不是特征模板版本。

`.bin` 和数据库保留完整帧，PNG 仅用于显示。历史分析曾对另行导出的 16 位 PNG 回读验证全部 6,080 个数值一致；当前 GUI 导出的是 8 位预览，不能作为无损数值归档。文件和数据库规范见[使用指南](usage.md)。
