# FT9362 设备能力与验证边界

对象为本机 USB `2808:0752`。硬件结论来自 2026-10-11 的独立协议诊断、libfprint 生命周期测试，以及 2026-10-12 的综合协议验证（时间均为 Asia/Shanghai）。前两类测试的驱动基线为 `9f7ef1a`；综合报告包含结构版本 1 的中断轮次和版本 2 的续测完成轮次，取消矩阵直接访问 libusb。Windows 行为来自 5.2.69.24 安装包的[静态分析](windows-reference.md)。扩展刷新、响应校验、事务边界取消和错误后重同步已在当前 C 驱动实现，但该采集流程尚待实机验收。

设备可返回 40 × 152 原始图像。持续接触时，仅普通读取不会保持刷新；加入条件扩展取图后可持续更新。普通状态 00 不等于物理抬手。应用唤醒返回 09，运行模式和深睡恢复未验证。

本文只保存非生物识别结论；原始帧、模板和帧摘要保存在本机私有报告中。使用方式见[使用指南](usage.md#设备测试与报告)，当前驱动协议见[协议文档](protocol.md)。

## 1. 证据范围

| 证据组 | 样本范围 | 用途 |
| --- | --- | --- |
| 信息与生命周期 | 基础查询 38 个响应；无手指缓冲、独占、重开、复位和等待取消测试 | 设备身份、协议与 USB 行为 |
| 协议诊断组 | 动作 258 个响应，对照 143 个；合计 65 次普通、32 次扩展取图 | 接触变化、通道更新与时序 |
| GUI 复测组 | 动作 238 个响应，对照 142 个；合计 65 次普通、32 次扩展取图 | 独立复现同一采集行为 |
| 综合验证组（版本 1） | 已记录 BCC 的 1,996 个响应通过离线一致性核验，其中普通图像 325 个、扩展图像 290 个；取消矩阵尝试 17/50 项 | 通道顺序、接触变化、连续采集及取消残留；整轮未完成 |
| 综合验证组（版本 2） | 50 项均有记录：21 项通过、28 项恢复失败、1 项前置阻断；10 次续测，最终健康检查与抬手检查完成 | 图像中断残留、独立恢复策略和续测行为 |

诊断串行独占接口 0。USB reset 只作用于所选指纹设备；没有进行固件写入、系统 suspend、整机电源策略修改或未知 ACPI 操作。

## 4. 协议封装和额外尾字节

请求为 `02 | L_hi L_lo | CMD/参数 | BCC`；BCC 是长度两字节和命令体的 XOR，不含起始 `02`。响应为 `02 | L_hi L_lo | STATUS/数据 | BCC`，逻辑长度为 `L+4`，数据长度为 `L-1`。成功状态为 `04`，它不是像素或手指状态。

| 查询 | 完整 OUT | 逻辑 / 实收响应长度 |
| --- | --- | --- |
| 版本 | `02 00 01 30 31` | 48 / 49 |
| 桥接状态 | `02 00 01 34 35` | 7 / 8 |
| 应用状态 | `02 00 03 80 01 02 80` | 7 / 8 |
| 尺寸 A | `02 00 03 80 03 01 81` | 6 / 7 |
| 尺寸 B | `02 00 03 80 04 01 86` | 6 / 7 |
| 加密标志 | `02 00 03 80 07 01 85` | 5 / 6，空 ACK |
| UID / 升级计数 | `02 00 01 3D 3C` / `02 00 01 3F 3E` | 5 / 6，状态 09 |
| 普通状态 | `02 00 03 80 02 01 80` | 6 / 7 |
| 普通取图 | `02 00 01 81 80` | 12,165 / 12,166 |
| 扩展状态 / 扩展取图 | `02 00 03 82 73 01 F3` / `02 00 03 82 76 01 F6` | 6 / 7；12,165 / 12,166 |

非生物识别异常响应：

```text
加密标志：02 00 01 04 05 | 93
UID / 升级计数：02 00 01 09 08 | 9e（不同前序下也见 5a、2e）
```

竖线左侧是完整逻辑包，右侧是包外字节。加密查询的 `05` 是 BCC，`93` 不是有效数据；不能读出“加密关闭”。

两次独立顺序实验中，尺寸 A 的逻辑响应始终是 `02 00 02 04 28 2e`，包外字节随前一响应变化：

| 前一查询 | 尺寸 A 的尾字节 | 前一响应同偏移 6 |
| --- | --- | --- |
| 版本 | `39` | ASCII 字符 `9` |
| 桥接状态 | `f8` | 桥接响应 BCC |
| 应用状态 | `f8` | 应用响应 BCC |

UID 的尾字节也分别对应前一尺寸 B、应用状态、尺寸 A 响应偏移 5 的 `9e`、`5a`、`2e`。IN 使用新建清零缓冲并按 actual_length 保存，因此不能用 Python 接收缓冲未清理解释。

**推断：部分固件发送路径复用缓冲，额外发送一个未覆盖的旧字节。** 尚未定位固件发送代码；加密查询的 `93` 和图像包最后一字节没有被同样的顺序实验解释。不能声称所有尾字节都已破解。图像应从偏移 4 取 12,160 字节，BCC 位于 12,164，额外字节位于 12,165；原始保存继续保留完整实收内容。

## 5. 图像与状态行为

### 无手指缓冲

每组两轮、各三次普通读取均在读取前得到普通状态 00，六次图像载荷完全相同，包括单设备 USB reset 与取消实验前后。信息与生命周期实验中，每次 OUT+IN 约 18.11–18.19 ms。它证明能读出固定缓冲，不能证明每次进行了新采样，也不能据此声称约 55 FPS。

无手指缓冲的来源仍无法区分为此前采样、校准图或其他固件缓存。本文不记录其像素范围或图像预览；原始数据只在本机私有报告中。

### 动作测试：按住、滚动、抬手、再按

两组使用相同动作序列，每个样本依次执行：普通状态→普通取图→普通状态→扩展状态→若为 05 则扩展取图。每轮人为等待 350 ms。

| 阶段 | 普通帧数 / 不同载荷数 | 取图前 → 后普通状态 | 扩展状态 |
| --- | --- | --- | --- |
| 无手指基线 | 3 / 1 | 00 → 00 | 06 |
| 第一次按住不动 | 8 / 8 | 01 → 00 | 05 |
| 保持接触、轻微滚动 | 8 / 8 | 01 → 00 | 05 |
| 抬手后 | 3 / 1 | 00 → 00 | 06 |
| 同一手指再次按住 | 8 / 8 | 01 → 00 | 05 |

每组动作测试的 24 次扩展读取均取得完整数据，且不与紧邻的前一普通帧逐字节相同。两类通道都能形成可观察的纹理，但这不是匹配准确率或图像质量算法验证。此序列同时访问两个通道，更新触发因素由下述通道对照区分。

### 通道对照：一次接触，固定 A→B→C→D

保持同一根手指接触、不主动移动；四阶段各取 8 个普通帧。普通状态前后查询与人为间隔保持一致。

| 阶段 | 普通取图之外的访问 | 普通帧不同载荷数 | 观测 |
| --- | --- | --- | --- |
| A | 无 | 1 / 8 | 首次读前 01，此后读前为 00；所有读后为 00 |
| B | 扩展状态 `82 73 01` | 1 / 8 | 状态一直 05，但图像与 A 相同 |
| C | 扩展状态，05 时再 `82 76 01` | 8 / 8 | 首个普通帧仍与 A/B 相同；第一次扩展取图后后续普通帧开始变化 |
| D | 无 | 1 / 8 | 得到 C 最后一次扩展访问后更新的一帧，此后再次固定 |

这支持：**扩展取图参与推进刷新或重新准备下一帧；仅查扩展状态不够；一次扩展访问也不会永久开启持续流模式。** 内部是否直接触发 ADC、交换缓冲或重置就绪标志，尚未恢复。两组均复现该结果；固定顺序重复仍不能替代随机顺序或冷启动等价性验证。

普通状态在手指仍接触时也会于读图后变成 00，至少受帧就绪/消费影响。因此测试中的抬手需要用户实际执行，不能仅用 00 自动认定已经抬手。扩展 05/06 与本次接触/离开相关，但未覆盖压力、错误、过热、电源切换等所有条件，不能直接命名为纯物理接触位。

### 时序与帧率

| 量 | 协议诊断组 | GUI 复测组 | 限制 |
| --- | --- | --- | --- |
| 普通图像 OUT+IN | 阶段中位数约 18.5–19.1 ms | 约 19.0–19.4 ms | 可传输重复图像 |
| 扩展图像 OUT+IN | 约 101.9–105.2 ms | 约 103.3–104.5 ms | 不等于传感器额定帧率 |
| C 阶段普通帧接收间隔 | 中位数约 488.5 ms | 约 490.5 ms | 包含 350 ms 等待、两条图像路径及查询 |
| A/B/D 阶段接收间隔 | 约 378–385 ms | 未单列统计 | 内容重复，不能视作新样本帧率 |

基础小包查询曾测得约 0.096–0.241 ms，也观测到桥接状态和主密钥状态查询约 85 ms。响应时间并不恒定；长延迟与 STALL 的关系未确定。最高新样本速率、首帧稳定性、长期连续接触和温度影响尚未测定。

两个综合组均在轮前刷新缓冲，通道顺序为普通→附加扩展状态→条件扩展取图→条件扩展取图→附加扩展状态→普通，每阶段 10 帧。下表的载荷数按各阶段独立统计，不跨阶段或跨轮合并。

| 观测项 | 综合组版本 1 | 综合组版本 2 |
| --- | --- | --- |
| 普通、附加扩展状态阶段：不同普通载荷 / 帧数 | 四个阶段各 1/10 | 四个阶段各 1/10 |
| 条件扩展取图阶段：不同普通载荷 / 帧数 | 两个阶段各 10/10 | 两个阶段各 10/10 |

| 抬手后三次普通载荷 | 相同 | 相同 |

两组均观测到条件扩展取图期间普通载荷持续变化，且抬手后普通状态仍可出现 01；普通 01 不能单独证明物理接触。实验未区分固件内部的采样触发、缓冲交换或就绪标志机制。

版本 1 综合组的完整图像响应均为 12,166 字节。动作按提示执行，没有独立压力测量。连续阶段每轮包含 100 ms 人为等待、查询与报告开销；上述速率不代表最高帧率、热稳定性或识别质量。“未单列统计”不表示该轮没有相应响应。

## 6. USB、电源与取消

### 接口、电源与生命周期

| 项目 | 实测结果 | 不能推广的结论 |
| --- | --- | --- |
| 立即 / 0.5 s 后重开 | 基线查询正常 | 未模拟崩溃 |
| 3 / 6 s 后重开 | 既有首次 open IO、同端口重枚举后重试成功，也有 suspended 状态直接打开成功 | 故障并非必现，原因未定位 |
| 自动挂起后的初次打开 | 多次在任何私有 OUT 前 IO，内核记录 disconnect 与新地址 | 不证明每次都失败 |
| 第二句柄 claim | BUSY=`-6`，首句柄仍正常 | 应先停止预览再测试 |
| clear-halt IN/OUT | 均返回 0，随后基线正常 | 此组初始无 halt；故障注入结果见下方版本 2 矩阵 |
| 单设备 USB reset | 返回 0，重开后版本、就绪、尺寸与状态正常 | 不等于断电或 MCU 全重启 |
| 标准 GET_INTERFACE | 两次 EP0 STALL；后续 SETUP 与 Bulk 正常 | 不等于整个接口不可用；未测 SET_INTERFACE |
| 预取消、等待手指取消 | 信息与生命周期两轮、GUI 复测一轮；每轮 0/250/750/1500/250 ms 均 CANCELLED | 未覆盖取图传输中途取消 |
| 取消后再启动、关闭重开 | 已测轮次均成功 | 未证明真实匹配或新鲜图像识别 |
| remote wakeup | 描述符声明，系统未启用 | 未让系统睡眠、未验证整机唤醒 |

上述重开实验中，诊断工具对 `open USB` 阶段的 IO / NO_DEVICE 在等待 600 ms 后进行一次重新枚举，要求目标唯一且同一物理端口；权限或 BUSY 错误不重试，已发送命令不重发。当前驱动的设备对象生命周期见[开发指南](development.md#驱动生命周期)。

等待取消的延迟测得约 0.21–0.36 ms，GUI 复测约 0.45–0.61 ms；预取消约 1.3–1.47 ms。这些是观测值，不是实时性上限。libfprint 曾报告无法禁用 USB persist，实测属性保持 1。

**已知通信异常：** raw 00 和心跳成功后，桥接状态查询曾在 Bulk IN 返回 `LIBUSB_ERROR_PIPE (-9)`，实收 0 字节；当时尚未发送应用唤醒。也存在相同序列成功的记录，根因未确定。该序列期间观测到的 STALL 尚无受控恢复结论，不能据此确认 raw 00 是原因。下述取消矩阵的续测记录属于另一类故障条件。

### 取消实验条件与覆盖范围

取消矩阵直接使用 libusb，两个版本的探测和清理条件不同，结果分别保留。实验机制见[开发指南](development.md#综合协议验证)。

| 条件 / 结果 | 综合组版本 1 | 综合组版本 2 |
| --- | --- | --- |
| 恢复后的桥接探测 IN 容量 | 64 字节 | 12,224 字节，可容纳完整图像响应 |
| 用例间独立清理 | 无版本 2 的独立清理流程 | 测量后单独排空、检查并释放接口；清理结果不改变测量结果 |
| 已尝试 / 总项数 | 17/50 | 50/50 |
| 结果 | 12 通过、4 恢复失败、1 基线失败 | 21 通过、28 恢复失败、1 前置阻断 |
| 最终收尾 | 未执行 | 健康查询、扩展状态 06 和接口释放完成 |

两个版本的五个对照（不提交、普通/扩展完整事务、普通/扩展首块后记录取消意图但读完）均通过健康查询和后续三帧采集。后两项没有中止进行中的 USB 传输；这些直接协议实验不等于当前 C 驱动取消流程的实机验收。

### 独立恢复方式与残留响应

下表为版本 2 的 45 个中断与恢复组合，另五项为上述对照。

| 中断位置 | 直接继续 | 有界排空 | 仅 clear-halt | 仅重开 | 仅 reset |
| --- | --- | --- | --- | --- | --- |
| 普通状态 OUT | 失败 | 通过 | 失败 | 失败 | 通过 |
| 普通状态 IN | 通过 | 通过 | 通过 | 通过 | 通过 |
| 普通图像 OUT | 失败 | 通过 | 失败 | 失败 | 失败 |
| 普通图像 IN，1 ms | 失败 | 通过 | 失败 | 失败 | 失败 |
| 普通图像首 4096 字节后 | 失败 | 通过 | 失败 | 失败 | 失败 |
| 扩展图像 OUT | 失败 | 通过 | 失败 | 失败 | 通过 |
| 扩展图像 IN，1 ms | 失败 | 通过 | 失败 | 失败 | 前置阻断 |
| 扩展图像 IN，50 ms | 失败 | 通过 | 失败 | 失败 | 通过 |
| 扩展图像首 4096 字节后 | 失败 | 通过 | 失败 | 失败 | 失败 |

“通过”包括指定恢复后的健康查询及三次采集；“失败”表示指定恢复未通过，后续独立清理不改变该结果。普通状态 IN 五项的取消回调已交付完整 7 字节应答，没有覆盖状态半包。

普通状态 OUT 取消时已写出全部 7 字节，普通取图 OUT 取消时已写出全部 5 字节。直接继续、clear-halt 和重开后的查询读到旧响应。九个排空项全部通过，取消时已收字节与排空残留可重建旧响应且 BCC 均有效：普通 IN 1 ms 排空项为 832 + 11,334 字节；普通和扩展首块中断项均为 4096 + 8070 字节；扩展 IN 1 ms、50 ms 项在取消时实收 0，排空各收到 12,166 字节。

四个 reset 恢复失败项的独立清理也失败，触发暂停；其余恢复失败项的独立清理通过。reset 返回 0 后仍出现桥接 OUT 全部写出而 IN 超时、随后清理查询 OUT 也超时的记录。此处 reset 的测量不附带排空。

第 40 项（扩展 IN 1 ms / reset）在接触前提检查收到数据 00：封包 BCC 和成功状态有效，桥接、应用、尺寸查询均通过。该项未注入中断、未执行被测 reset，不能计为 reset 恢复失败。其他续测的接触前提也出现过同类 00；没有证据将它解释为物理抬手或接触就绪。

版本 1 在已覆盖的状态命令场景中得到相同的恢复方式结果：状态 OUT 的直接继续、clear-halt、重开均先读到旧状态响应，排空与 reset 通过；排空实际读到旧 7 字节响应。状态 OUT 取消时已写出全部 7 字节，状态 IN 的五种恢复方式均通过，但回调已交付完整 7 字节，未覆盖状态半包。

版本 1 特有的小缓冲条件下，普通图像 OUT 取消时已写出全部 5 字节；直接继续后的桥接查询只收到 64 字节旧图像片段，其头部为 `02 2F 81 04`，不是桥接命令拒绝响应。下一项普通图像 OUT / 排空在基线阶段出现 reset 返回 0、排空超时而桥接仍超时，未进入故障注入或指定恢复，不能记为排空策略失败。此后其余 33 项未开始。失联原因未定位，不能断言固件因短读锁死，也不能把这一条件与版本 2 的完整容量探测混合统计。

### 等待、重开与恢复观察

版本 2 有 10 次续测。每次不持有句柄地按 2、5、15、30 秒逐级等待，随后重开并查询；首次健康检查通过就结束本次等待序列。有的在 2 秒检查通过，有的依次失败后在 5、15 或 30 秒检查通过。部分重开需要第二次打开尝试，涉及同端口重新枚举。通信检查通过后仍可能因扩展状态 00 暂停。

这测量的是等待、重开和查询的组合，等待值是各次独立延迟，不能记为从故障发生起的固定恢复时间，也没有隔离自动挂起的影响。续测及最终收尾没有改写先前 28 个恢复失败和 1 个前置阻断结果。

### USB 断开与重枚举

系统 journal 的内核及服务日志包含以下事件，日期均为 2026-10-12；设备为同一物理端口 `3-3.3` 的 `2808:0752`。

| 时间 | 观测 |
| --- | --- |
| 01:42:18、01:42:51、01:42:55、01:43:01、01:43:13、01:45:55、01:46:00 | 断开并重新枚举，USB 地址依次由 14 增至 21 |
| 01:43:28 | 复位过程中设置地址请求未获设备响应 |
| 01:58:23 | 综合轮次结束后，系统 fprintd 启动 |
| 01:58:24、01:58:28 | fprintd 打开当时的设备节点分别返回 errno=5（I/O 错误）；同一时段断开、重新枚举，地址由 21→22→23 |
| 02:05 | 只读检查时地址仍为 23，电源属性为 `control=auto`、`runtime_status=suspended` |
| 02:30:15、02:30:19 | 系统 fprintd 于 02:30:15 启动；两次打开旧设备节点均返回 errno=5，同时发生断开、重枚举，地址由 23→24→25 |
| 02:31:26 | fprintd 正常退出 |
| 02:31:52 | 只读检查时地址为 25，`control=auto`、`runtime_status=suspended`、`autosuspend_delay_ms=2000`、`persist=0` |

02:30 时段 journal 记录了同一个 Ghostty 终端作用域内三次 `sudo -v` 的认证失败，时间分别为 02:30:17、02:30:20、02:30:24；系统 sudo 的 PAM 配置启用了 `pam_fprintd.so`，顺序在密码认证之前。这与 fprintd 启动、打开设备和 02:30:23 停止验证的时段一致。操作者确认这些命令是在听到提示音后主动执行，用于测试指纹识别；因此不能用这三次认证解释更早听到的声音。

可读取的内核 journal 在 02:00:00 至 02:30:15 之前没有事件记录；该区间的系统服务日志只记录 fprintd 于 02:00:41 退出，未见再次启动。02:30:15、02:30:19 的断开有日志确认，但更早提示音的精确时间和来源没有确定，不能据此补推一次未记录的指纹设备重枚举。

该时段系统服务使用的 libfprint 安装包，其 FT9362 源码与提交 `9f7ef1a` 一致，未包含当前工作树的取消及同步修改。该版没有主动 USB reset 或 clear-halt；超时路径结束动作并报错，名为 `capture_reset` 的函数只清理主机缓存。libfprint 在调用驱动 open 回调前先打开 USB；上述两次错误发生于 libusb 打开设备节点时，该次打开未进入驱动采集。该时段内核日志记录的是 disconnect / new device，没有显式 reset 记录。

日志中的大量 reset 与测试主动复位时段重合，不能全部计为自发故障。两段 fprintd 打开错误均与断开出现在同一时段，未证明打开操作导致断开，也未区分固件、电源恢复或 USB 栈的根因。02:05 和 02:31 的电源属性均是事后观测，不证明故障瞬间的状态，也不是私有协议健康检查。系统所用 libfprint 有将 USB persist 设为 0 的通用电源管理路径；属性为 0 本身不是主动复位记录。

操作者报告恢复过程中似乎听到 GNOME 的设备连接提示音；没有精确时间戳，未将该声音与某条重枚举事件一一对应。
