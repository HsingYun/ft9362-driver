# FT9362 设备能力与验证边界

对象为本机 USB `2808:0752`。硬件结论来自 2026-10-11 的独立协议诊断、libfprint 生命周期测试，以及 2026-10-12 的综合协议验证（时间均为 Asia/Shanghai）。前两类测试的驱动基线为 `9f7ef1a`；综合报告结构版本为 1，取消矩阵直接访问 libusb。Windows 行为来自 5.2.69.24 安装包的[静态分析](windows-reference.md)。扩展刷新和响应校验已在当前 C 驱动实现，但该采集流程尚待实机验收。

设备可返回 40 × 152 原始图像。持续接触时，仅普通读取不会保持刷新；加入条件扩展取图后可持续更新。普通状态 00 不等于物理抬手。应用唤醒返回 09，运行模式和深睡恢复未验证。

本文只保存非生物识别结论；原始帧、模板和帧摘要保存在本机私有报告中。使用方式见[使用指南](usage.md#设备测试与报告)，当前驱动协议见[协议文档](protocol.md)。

| 证据组 | 样本范围 | 用途 |
| --- | --- | --- |
| 信息与生命周期 | 基础查询 38 个响应；无手指缓冲、独占、重开、复位和等待取消测试 | 设备身份、协议与 USB 行为 |
| 协议诊断组 | 动作 258 个响应，对照 143 个；合计 65 次普通、32 次扩展取图 | 接触变化、通道更新与时序 |
| GUI 复测组 | 动作 238 个响应，对照 142 个；合计 65 次普通、32 次扩展取图 | 独立复现同一采集行为 |
| 综合验证组 | 已记录 BCC 的 1,996 个响应通过离线一致性核验，其中普通图像 325 个、扩展图像 290 个；取消矩阵尝试 17/50 项 | 通道顺序、接触变化、连续采集及取消残留；整轮未完成 |

各组分别核验响应、实际 IN 字节及保存样本的一致性，不合并其响应数量或时序统计。综合组的 1,996 个响应包括校验有效但语义拒绝的应答，不等于 1,996 次命令成功；中断产生的不完整数据另行保存。手指动作由操作者按提示执行，不是独立的接触或压力测量。

诊断串行独占接口 0。USB reset 只作用于所选指纹设备；没有进行固件写入、系统 suspend、整机电源策略修改或未知 ACPI 操作。

## 4. 协议封装和额外尾字节

请求为 `02 | L_hi L_lo | CMD/参数 | BCC`；BCC 是长度两字节和命令体的 XOR，不含起始 `02`。响应为 `02 | L_hi L_lo | STATUS/数据 | BCC`，逻辑长度为 `L+4`，数据长度为 `L-1`。成功状态为 `04`，它不是像素或手指状态。

| 查询 | 完整 OUT | 逻辑 / 实收响应长度 |
| --- | --- | --- |
| 版本 | `02 00 01 30 31` | 48 / 49 |
| 桥接状态 | `02 00 01 34 35` | 7 / 8 |
| 应用状态 | `02 00 03 80 01 02 80` | 7 / 8 |
| 尺寸 A | `02 00 03 80 03 01 81` | 6 / 7 |
| 尺寸 B | `02 00 03 80 04 01 86` | 6 / 7 |
| 加密标志 | `02 00 03 80 07 01 85` | 5 / 6，空 ACK |
| UID / 升级计数 | `02 00 01 3D 3C` / `02 00 01 3F 3E` | 5 / 6，状态 09 |
| 普通状态 | `02 00 03 80 02 01 80` | 6 / 7 |
| 普通取图 | `02 00 01 81 80` | 12,165 / 12,166 |
| 扩展状态 / 扩展取图 | `02 00 03 82 73 01 F3` / `02 00 03 82 76 01 F6` | 6 / 7；12,165 / 12,166 |

非生物识别异常响应：

```text
加密标志：02 00 01 04 05 | 93
UID / 升级计数：02 00 01 09 08 | 9e（不同前序下也见 5a、2e）
```

竖线左侧是完整逻辑包，右侧是包外字节。加密查询的 `05` 是 BCC，`93` 不是有效数据；不能读出“加密关闭”。

两次独立顺序实验中，尺寸 A 的逻辑响应始终是 `02 00 02 04 28 2e`，包外字节随前一响应变化：

| 前一查询 | 尺寸 A 的尾字节 | 前一响应同偏移 6 |
| --- | --- | --- |
| 版本 | `39` | ASCII 字符 `9` |
| 桥接状态 | `f8` | 桥接响应 BCC |
| 应用状态 | `f8` | 应用响应 BCC |

UID 的尾字节也分别对应前一尺寸 B、应用状态、尺寸 A 响应偏移 5 的 `9e`、`5a`、`2e`。IN 使用新建清零缓冲并按 actual_length 保存，因此不能用 Python 接收缓冲未清理解释。

**推断：部分固件发送路径复用缓冲，额外发送一个未覆盖的旧字节。** 尚未定位固件发送代码；加密查询的 `93` 和图像包最后一字节没有被同样的顺序实验解释。不能声称所有尾字节都已破解。图像应从偏移 4 取 12,160 字节，BCC 位于 12,164，额外字节位于 12,165；原始保存继续保留完整实收内容。

## 5. 图像与状态行为

### 无手指缓冲

每组两轮、各三次普通读取均在读取前得到普通状态 00，六次图像载荷完全相同，包括单设备 USB reset 与取消实验前后。信息与生命周期实验中，每次 OUT+IN 约 18.11–18.19 ms。它证明能读出固定缓冲，不能证明每次进行了新采样，也不能据此声称约 55 FPS。

无手指缓冲的来源仍无法区分为此前采样、校准图或其他固件缓存。本文不记录其像素范围或图像预览；原始数据只在本机私有报告中。

### 动作测试：按住、滚动、抬手、再按

两组使用相同动作序列，每个样本依次执行：普通状态→普通取图→普通状态→扩展状态→若为 05 则扩展取图。每轮人为等待 350 ms。

| 阶段 | 普通帧数 / 不同载荷数 | 取图前 → 后普通状态 | 扩展状态 |
| --- | --- | --- | --- |
| 无手指基线 | 3 / 1 | 00 → 00 | 06 |
| 第一次按住不动 | 8 / 8 | 01 → 00 | 05 |
| 保持接触、轻微滚动 | 8 / 8 | 01 → 00 | 05 |
| 抬手后 | 3 / 1 | 00 → 00 | 06 |
| 同一手指再次按住 | 8 / 8 | 01 → 00 | 05 |

每组动作测试的 24 次扩展读取均取得完整数据，且不与紧邻的前一普通帧逐字节相同。两类通道都能形成可观察的纹理，但这不是匹配准确率或图像质量算法验证。此序列同时访问两个通道，更新触发因素由下述通道对照区分。

### 通道对照：一次接触，固定 A→B→C→D

保持同一根手指接触、不主动移动；四阶段各取 8 个普通帧。普通状态前后查询与人为间隔保持一致。

| 阶段 | 普通取图之外的访问 | 普通帧不同载荷数 | 观测 |
| --- | --- | --- | --- |
| A | 无 | 1 / 8 | 首次读前 01，此后读前为 00；所有读后为 00 |
| B | 扩展状态 `82 73 01` | 1 / 8 | 状态一直 05，但图像与 A 相同 |
| C | 扩展状态，05 时再 `82 76 01` | 8 / 8 | 首个普通帧仍与 A/B 相同；第一次扩展取图后后续普通帧开始变化 |
| D | 无 | 1 / 8 | 得到 C 最后一次扩展访问后更新的一帧，此后再次固定 |

这支持：**扩展取图参与推进刷新或重新准备下一帧；仅查扩展状态不够；一次扩展访问也不会永久开启持续流模式。** 内部是否直接触发 ADC、交换缓冲或重置就绪标志，尚未恢复。两组均复现该结果；固定顺序重复仍不能替代随机顺序或冷启动等价性验证。

普通状态在手指仍接触时也会于读图后变成 00，至少受帧就绪/消费影响。因此测试中的抬手需要用户实际执行，不能仅用 00 自动认定已经抬手。扩展 05/06 与本次接触/离开相关，但未覆盖压力、错误、过热、电源切换等所有条件，不能直接命名为纯物理接触位。

### 时序与帧率

| 量 | 协议诊断组 | GUI 复测组 | 限制 |
| --- | --- | --- | --- |
| 普通图像 OUT+IN | 阶段中位数约 18.5–19.1 ms | 约 19.0–19.4 ms | 可传输重复图像 |
| 扩展图像 OUT+IN | 约 101.9–105.2 ms | 约 103.3–104.5 ms | 不等于传感器额定帧率 |
| C 阶段普通帧接收间隔 | 中位数约 488.5 ms | 约 490.5 ms | 包含 350 ms 等待、两条图像路径及查询 |
| A/B/D 阶段接收间隔 | 约 378–385 ms | 未单列统计 | 内容重复，不能视作新样本帧率 |

基础小包查询曾测得约 0.096–0.241 ms，也观测到桥接状态和主密钥状态查询约 85 ms。响应时间并不恒定；长延迟与 STALL 的关系未确定。最高新样本速率、首帧稳定性、长期连续接触和温度影响尚未测定。

### 综合采样：访问顺序、接触变化与连续性

综合组的通道顺序为普通→附加扩展状态→条件扩展取图→条件扩展取图→附加扩展状态→普通，每阶段 10 帧。两次普通阶段及两次附加状态阶段均只有 1 个不同普通载荷；两次条件扩展取图阶段均为 10 个不同载荷。轮前已刷新缓冲，结果继续支持扩展取图参与推进更新，不能据此确认固件内部缓冲机制。

轻触、正常按压分别得到 12/12 个不同普通载荷，滚动为 16/16；动作按提示执行，没有独立压力测量。连续阶段 60.13 秒取得 178 个不同普通载荷和 178 个扩展响应，包含每轮 100 ms 等待、查询与报告开销；交付速率约 2.96 帧/秒，普通帧间隔中位数 335.71 ms、最大 401.46 ms。该结果证明此阶段能连续取得变化数据，不代表最高帧率、热稳定性或识别质量。

综合组完整图像响应均为 12,166 字节；普通和扩展 USB 事务耗时中位数分别约 17.51 ms、97.43 ms。抬手阶段三次扩展状态均为 06，普通读前状态却依次为 **01、00、00**，三次普通载荷相同。因此普通 01 也不能单独证明物理接触；它可以表示尚未消费的就绪帧。

## 6. USB、电源与取消

| 项目 | 实测结果 | 不能推广的结论 |
| --- | --- | --- |
| 立即 / 0.5 s 后重开 | 基线查询正常 | 未模拟崩溃 |
| 3 / 6 s 后重开 | 既有首次 open IO、同端口重枚举后重试成功，也有 suspended 状态直接打开成功 | 故障并非必现，原因未定位 |
| 自动挂起后的初次打开 | 多次在任何私有 OUT 前 IO，内核记录 disconnect 与新地址 | 不证明每次都失败 |
| 第二句柄 claim | BUSY=`-6`，首句柄仍正常 | 应先停止预览再测试 |
| clear-halt IN/OUT | 均返回 0，随后基线正常 | 初始无 halt，未验证故障注入后的恢复 |
| 单设备 USB reset | 返回 0，重开后版本、就绪、尺寸与状态正常 | 不等于断电或 MCU 全重启 |
| 标准 GET_INTERFACE | 两次 EP0 STALL；后续 SETUP 与 Bulk 正常 | 不等于整个接口不可用；未测 SET_INTERFACE |
| 预取消、等待手指取消 | 信息与生命周期两轮、GUI 复测一轮；每轮 0/250/750/1500/250 ms 均 CANCELLED | 未覆盖取图传输中途取消 |
| 取消后再启动、关闭重开 | 已测轮次均成功 | 未证明真实匹配或新鲜图像识别 |
| remote wakeup | 描述符声明，系统未启用 | 未让系统睡眠、未验证整机唤醒 |

诊断工具只对 `open USB` 阶段的 IO / NO_DEVICE 在等待 600 ms 后进行一次重新枚举，要求目标唯一且同一物理端口；不重试权限或 BUSY 错误，也不在已发送命令后盲目重发。正式驱动需要处理重枚举对象失效，不能用旧地址或旧句柄无限重试。

等待取消的延迟测得约 0.21–0.36 ms，GUI 复测约 0.45–0.61 ms；预取消约 1.3–1.47 ms。这些是观测值，不是实时性上限。libfprint 曾报告无法禁用 USB persist，实测属性保持 1。

**已知通信异常：** raw 00 和心跳成功后，桥接状态查询曾在 Bulk IN 返回 `LIBUSB_ERROR_PIPE (-9)`，实收 0 字节；当时尚未发送应用唤醒。也存在相同序列成功的记录，根因未确定。真实 Bulk 故障后的向导恢复与续测尚未完成实机验证，正常状态下 reset 成功不能替代此项证据。

### 取消后的残留响应

综合组取消矩阵记录为 12 项通过、4 项恢复失败、1 项基线失败，其余 33 项未开始。这里的通过只覆盖该项实际命中的时机和后续查询，不代表所有图像传输取消都能恢复。

| 中断条件 | 观测 | 驱动含义 |
| --- | --- | --- |
| 不提交目标命令、完整普通/扩展事务、首块后记录取消意图但读完整帧 | 5 个对照均通过健康查询和后续三帧采集 | 完成当前协议事务后结束动作值得验证；不是正在进行的 USB 传输被取消 |
| 普通状态 OUT 取消 | 取消成功，实际已写出全部 7 字节；直接继续、仅 clear-halt、仅 reopen 时，桥接查询先读到旧状态响应 | USB 取消不能撤回已送达命令；清除 halt 和关闭句柄不等于清空设备应答 |
| 同一状态 OUT 中断，有界 drain / 单设备 reset | 两项后续查询及三帧采集通过；drain 实际读到旧 7 字节响应 | 只证明小状态响应场景，不能推广到图像半包 |
| 普通状态 IN 取消 | 5 种恢复方式均通过，但取消回调已交付全部 7 字节状态响应 | 没有覆盖未收完状态响应或图像响应的情况 |
| 普通图像 OUT 取消，直接继续 | 实际已写出全部 5 字节；桥接查询的 64 字节 IN 收到以 `02 2F 81 04` 开始的旧图像片段 | 此时不能将该应答归为桥接命令拒绝；测试的小缓冲读取自身也会影响残留状态 |
| 下一项普通图像 OUT / drain 的基线 | reset 返回 0、排空读到空超时，但桥接查询仍超时；未进入故障注入或指定恢复 | 这是基线失败，不能记为 drain 策略无效；reset 返回成功不保证私有协议就绪 |

旧图像被读取 64 字节之后的失联原因尚未定位，不能断言固件必然因短读锁死。该报告未覆盖其余图像 IN、半包、扩展通道中断组合，也未执行最终恢复阶段。当前测试使用完整图像容量探测，并把测量结果与用例清理分开记录，机制见[开发指南](development.md#综合协议验证)；此修订仍需设备复测。

## 7. 当前 Linux 实现与验证状态

| 能力 | 当前实现 | 验证边界 |
| --- | --- | --- |
| 持续采集 | 同一状态机执行普通与扩展查询、取图；只交付普通帧 | 软件模拟通过，新的 libfprint 采集流程尚待实机验收 |
| 响应校验 | 检查起始标记、长度、BCC、设备状态和载荷边界；分块共享截止时间 | 不能识别所有格式合法的陈旧响应 |
| 模板与匹配 | 单帧 enroll，原始帧模板；verify 旁路成功，identify 选择非空图库首项 | 不具备身份认证能力 |
| API 声明 | PRESS、一个录入阶段、VERIFY / IDENTIFY | 无标准 CAPTURE 或设备模板 STORAGE / LIST / DELETE / CLEAR 声明；device_id 为占位值 `0` |
| 设备恢复 | 生产驱动结束错误动作；诊断工具提供独立 drain、clear-halt、reopen、reset 实验 | 生产驱动尚无取消后自动重同步 |
| 初始化与电源 | open/close 仅管理接口；没有设备专用唤醒、模式或休眠流程 | Linux USB 电源管理不等于完成芯片初始化 |
| 图像处理 | 保存完整原始帧，Python 仅做显示拉伸 | 无解密、采集质量门槛或 Windows 预处理等价实现 |
| 校准与自检 | 无对应芯片命令 | USB reset、Windows 占位应答不能证明硬件校准或自检通过 |

详细状态机与接口契约见[开发指南](development.md)，Windows 条件路径与型号差异见[移植参考](windows-reference.md)。GUI 诊断直接访问 USB，其成功不等于 libfprint 采集流程已通过相同实机测试。
