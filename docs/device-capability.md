# FT9362 当前设备能力与 Linux / Windows 行为对照

核对日期：2026-10-11（Asia/Shanghai）。测试对象为本机 USB `2808:0752`；驱动基线提交 `9f7ef1a`。本文合并此前的信息探测、无手指能力测试、手指动作和通道对照三份结果，作为统一的实测记录。Windows 对照来自用户提供的 **5.2.69.24** 安装包的[静态分析](windows-reference.md)，不是在 Windows 上重新运行硬件测试。

**当前已确认：设备能返回 40 × 152 的原始图像；仅普通读取不会在持续按住时保持刷新，加入条件扩展取图后可以持续更新。普通状态 00 不能直接等同于抬手。基础信息、心跳、接口独占、USB 重开/复位和等待手指时取消已实测；应用唤醒返回 09，模式和深睡恢复没有验证通过。**

本文不包含指纹图像、原始像素、模板、帧哈希、手指名称或能用于重建指纹的样本。保留设备信息、命令、状态、时序和非生物识别统计，不收录本机原始证据文件或报告索引。本文可独立阅读；需要复核时，按 GUI 测试流程重新生成报告。

## 4. 协议封装和额外尾字节

请求为 `02 | L_hi L_lo | CMD/参数 | BCC`；BCC 是长度两字节和命令体的 XOR，不含起始 `02`。响应为 `02 | L_hi L_lo | STATUS/数据 | BCC`，逻辑长度为 `L+4`，数据长度为 `L-1`。成功状态为 `04`，它不是像素或手指状态。

| 查询 | 完整 OUT | 逻辑 / 实收响应长度 |
| --- | --- | --- |
| 版本 | `02 00 01 30 31` | 48 / 49 |
| 桥接状态 | `02 00 01 34 35` | 7 / 8 |
| 应用状态 | `02 00 03 80 01 02 80` | 7 / 8 |
| 尺寸 A | `02 00 03 80 03 01 81` | 6 / 7 |
| 尺寸 B | `02 00 03 80 04 01 86` | 6 / 7 |
| 加密标志 | `02 00 03 80 07 01 85` | 5 / 6，空 ACK |
| UID / 升级计数 | `02 00 01 3D 3C` / `02 00 01 3F 3E` | 5 / 6，状态 09 |
| 普通状态 | `02 00 03 80 02 01 80` | 6 / 7 |
| 普通取图 | `02 00 01 81 80` | 12,165 / 12,166 |
| 扩展状态 / 扩展取图 | `02 00 03 82 73 01 F3` / `02 00 03 82 76 01 F6` | 6 / 7；12,165 / 12,166 |

非生物识别异常响应：

```text
加密标志：02 00 01 04 05 | 93
UID / 升级计数：02 00 01 09 08 | 9e（不同前序下也见 5a、2e）
```

竖线左侧是完整逻辑包，右侧是包外字节。加密查询的 `05` 是 BCC，`93` 不是有效数据；不能读出“加密关闭”。

两次独立顺序实验中，尺寸 A 的逻辑响应始终是 `02 00 02 04 28 2e`，包外字节随前一响应变化：

| 前一查询 | 尺寸 A 的尾字节 | 前一响应同偏移 6 |
| --- | --- | --- |
| 版本 | `39` | ASCII 字符 `9` |
| 桥接状态 | `f8` | 桥接响应 BCC |
| 应用状态 | `f8` | 应用响应 BCC |

UID 的尾字节也分别对应前一尺寸 B、应用状态、尺寸 A 响应偏移 5 的 `9e`、`5a`、`2e`。IN 使用新建清零缓冲并按 actual_length 保存，因此不能用 Python 接收缓冲未清理解释。

**推断：部分固件发送路径复用缓冲，额外发送一个未覆盖的旧字节。** 尚未定位固件发送代码；加密查询的 `93` 和图像包最后一字节没有被同样的顺序实验解释。不能声称所有尾字节都已破解。图像应从偏移 4 取 12,160 字节，BCC 位于 12,164，额外字节位于 12,165；原始保存继续保留完整实收内容。

## 5. 无手指与有手指的真实图像行为

### 无手指缓冲

两轮各三次普通读取均在读取前得到普通状态 00，六次图像载荷完全相同，包括单设备 USB reset 与取消实验前后。每次 OUT+IN 约 18.11–18.19 ms。它证明能读出固定缓冲，不能证明每次进行了新采样，也不能据此声称约 55 FPS。

无手指缓冲的来源仍无法区分为此前采样、校准图或其他固件缓存。本文不记录其像素范围或图像预览；原始数据只在本机私有报告中。

### 动作测试：按住、滚动、抬手、再按

每个样本依次执行：普通状态→普通取图→普通状态→扩展状态→若为 05 则扩展取图。每轮人为等待 350 ms。

| 阶段 | 普通帧数 / 不同载荷数 | 取图前 → 后普通状态 | 扩展状态 |
| --- | --- | --- | --- |
| 无手指基线 | 3 / 1 | 00 → 00 | 06 |
| 第一次按住不动 | 8 / 8 | 01 → 00 | 05 |
| 保持接触、轻微滚动 | 8 / 8 | 01 → 00 | 05 |
| 抬手后 | 3 / 1 | 00 → 00 | 06 |
| 同一手指再次按住 | 8 / 8 | 01 → 00 | 05 |

24 次扩展读取均取得完整数据，且不与紧邻的前一普通帧逐字节相同。两类通道都能形成可观察的纹理，但这不是匹配准确率或图像质量算法验证。这轮混用了两个通道，因此单独看它还不能确定更新触发因素。

### 通道对照：一次接触，固定 A→B→C→D

保持同一根手指接触、不主动移动；四阶段各取 8 个普通帧。普通状态前后查询与人为间隔保持一致。

| 阶段 | 普通取图之外的访问 | 普通帧不同载荷数 | 观测 |
| --- | --- | --- | --- |
| A | 无 | 1 / 8 | 首次读前 01，此后读前为 00；所有读后为 00 |
| B | 扩展状态 `82 73 01` | 1 / 8 | 状态一直 05，但图像与 A 相同 |
| C | 扩展状态，05 时再 `82 76 01` | 8 / 8 | 首个普通帧仍与 A/B 相同；第一次扩展取图后后续普通帧开始变化 |
| D | 无 | 1 / 8 | 得到 C 最后一次扩展访问后更新的一帧，此后再次固定 |

这支持：**扩展取图参与推进刷新或重新准备下一帧；仅查扩展状态不够；一次扩展访问也不会永久开启持续流模式。** 内部是否直接触发 ADC、交换缓冲或重置就绪标志，尚未恢复。固定顺序、单轮测试不能替代随机顺序重复或冷启动等价性验证。

普通状态在手指仍接触时也会于读图后变成 00，至少受帧就绪/消费影响。因此测试中的抬手需要用户实际执行，不能仅用 00 自动认定已经抬手。扩展 05/06 与本次接触/离开相关，但未覆盖压力、错误、过热、电源切换等所有条件，不能直接命名为纯物理接触位。

### 时序与帧率

| 量 | 原始手指对照观测 | 限制 |
| --- | --- | --- |
| 普通图像 OUT+IN | 阶段中位数约 18.5–19.1 ms | 可传输重复图像 |
| 扩展图像 OUT+IN | 约 101.9–105.2 ms | 不直接等于额定 10 FPS |
| C 阶段普通帧接收间隔 | 中位数约 488.5 ms | 包含人为 350 ms 等待、两条图像路径及查询 |
| A/B/D 接收间隔 | 约 378–385 ms | 内容重复，不能视作新样本帧率 |
| 基础小包查询 OUT+IN | 原始探测约 0.096–0.241 ms | 不含初始化、重枚举，不是图像速率 |

目前只能确认持续接触存在更新路径，不能给出传感器最高新样本帧率。需要取消人为延迟、控制读取路径，再测首帧稳定、重复率、丢包、过热和持续运行。

## 6. USB、电源与取消

| 项目 | 实测结果 | 不能推广的结论 |
| --- | --- | --- |
| 立即 / 0.5 s 后重开 | 基线查询正常 | 未模拟崩溃 |
| 3 / 6 s 后重开 | 首次 open IO，同端口重枚举，一次重试后正常 | 未确定主控、桥接、固件或电源策略的单方原因 |
| 自动挂起后的初次打开 | 多次在任何私有 OUT 前 IO，内核记录 disconnect 与新地址 | 不证明每次都失败 |
| 第二句柄 claim | BUSY=`-6`，首句柄仍正常 | 应先停止预览再测试 |
| clear-halt IN/OUT | 均返回 0，随后基线正常 | 初始无 halt，未验证故障注入后的恢复 |
| 单设备 USB reset | 返回 0，重开后版本、就绪、尺寸与状态正常 | 不等于断电或 MCU 全重启 |
| 标准 GET_INTERFACE | 两次 EP0 STALL；后续 SETUP 与 Bulk 正常 | 不等于整个接口不可用；未测 SET_INTERFACE |
| 预取消、等待手指取消 | 两轮各 0/250/750/1500/250 ms，合计 10 次 CANCELLED | 未覆盖取图传输中途取消 |
| 取消后再启动、关闭重开 | 两轮均成功 | 未证明真实匹配或新鲜图像识别 |
| remote wakeup | 描述符声明，系统未启用 | 未让系统睡眠、未验证整机唤醒 |

诊断工具只对 `open USB` 阶段的 IO / NO_DEVICE 在等待 600 ms 后进行一次重新枚举，要求目标唯一且同一物理端口；不重试权限或 BUSY 错误，也不在已发送命令后盲目重发。正式驱动需要处理重枚举对象失效，不能用旧地址或旧句柄无限重试。

等待取消从定时回调到同步 API 返回约 0.21–0.36 ms，不含预取消；预取消约 1.3–1.47 ms。这不是实时性保证。第一次生命周期脚本退出有设备引用尚存警告，已调整 Python 对象释放顺序，第二轮未再出现；第二轮另有无法禁用 `power/persist` 的框架警告，随后属性仍为 1，未用 sudo 修改。

## 7. 真实行为对照 Linux 与 Windows

Linux 列指本仓库当前的[采集状态机](../driver/focaltech-0752.c)及[开发算法后端](../driver/algorithm/entry.cpp)。GUI 中的诊断访问是独立测试流程，不等于已移植到 libfprint 的生产采集状态机。

| 功能 | 当前 Linux 实现 | Windows 静态恢复的行为 | 本机验证对实现的影响 |
| --- | --- | --- | --- |
| 基础信息 | 主要使用固定设备与帧格式，未把全部查询纳入初始化 | 版本、尺寸、属性与能力缓存 | 版本/尺寸/两层就绪可用；UID、密钥状态等不能设为本机初始化必需项 |
| 普通采集 | 轮询普通状态，01 后 `81`，通过 enroll 返回原始帧 | 普通 Capture 另有主机处理和 WBDI 封装 | 普通缓冲可读，但一次接触后可能不再就绪 |
| 持续接触刷新 | 未接入扩展取图；提高 GUI 重绘频率无效 | GetMoreData 在 05 后发 `82 76 01`；另有 SCAN_IMAGE 模式 | 扩展读取确实推进更新；SCAN_IMAGE 本身仍未验证 |
| 手指状态映射 | 当前把就绪响应用于 PRESENT / NEEDED 等报告 | 存在普通与扩展状态的条件处理 | 应区分接触、就绪、消费，不能把普通 00 当纯抬手信号 |
| 图像布局 | 保存 12,166 字节；预览偏移 4、小端 16 位、40×152，显示分位拉伸 | 40×152 有专用预处理、解密/灰度/质量条件路径 | 采样布局有证据；GUI 拉伸不等于 Windows 图像处理逐像素一致 |
| 响应校验 | 普通状态检查最小长度/头/成功字节；图像按固定总长收齐，尚未统一校验 L/BCC | 共享协议封装带长度、状态和 BCC，部分主机路径有各自校验 | 诊断解析已按逻辑边界严格检查；后续需移植到 C 状态机，不能把诊断工具的检查误写成驱动已有 |
| 加密能力 | 原始数据保留，不据空响应补标志 | 按查询与分支条件处理 | 本机加密标志未知，不能凭 `DEC` 或图像可见断言关闭加密 |
| 初始化 / 电源 | 未移植完整 Windows 私有模式链 | raw 00、心跳、应用唤醒、87 写入及间接读等条件流程 | 应用唤醒 09，不能照搬全部共享路径 |
| USB 生命周期 | libfprint 负责异步取消与 close；有自动挂起重枚举问题 | WDF idle、锁、interrupt 管理等主机机制 | 等待取消有效；Windows 主机 API 不能直接当作 Linux 硬件命令 |
| 驱动 API 能力 | PRESS、enroll_stages=1、features=6（IDENTIFY / VERIFY），device_id=`0` | WBDI / BIR、引擎接口及模板流程 | 这些是主机声明，`0` 不是设备 UID；Linux 未声明标准 CAPTURE |
| 匹配 | verify 开发旁路成功；identify 返回首个图库候选；存的是原始帧 | 主机引擎、质量和模板导入导出契约 | 没有测试真正识别率，不能用于身份认证结论 |
| 设备模板存储 | 无 STORAGE / LIST / DELETE / CLEAR 声明 | 模板引擎接口不自动代表设备内存储 | 已恢复协议没有可确认的设备模板管理命令；不能推断硅片绝无存储 |
| Reset / Calibrate / GetTestRst | 没有相应真实芯片命令 | 部分 handler 为占位或未恢复动作 | USB reset 成功不能写成芯片校准或自检通过 |
| 平台集成 | 本次未改整机电源设置 | ACPI DSM、显示回调、C652 服务等型号/平台路径 | 不把其他型号与平台功能当成本机已支持 |

`SPIRead/SPIWrite`、`UsbBulkWriteRead` 是传输入口；本次通过已知有界请求验证 Bulk，不向这些入口注入未知命令。主机锁、ResumeIdle/StopIdle、clear/enable/disable interrupt 没有独立已知硬件测试命令。图像质量、模板算法和匹配是另一个验证层，不能由 USB ACK 推导正确性。

## 8. 在预览 GUI 中复现

```sh
nix develop -c python tools/capture.py
```

点击“设备测试…”。程序会结束当前录制、取消采集，等待 libfprint 关闭接口后打开测试向导。完整流程为 **20 步，共按压 3 次**；也可以选择仅无手指、仅动作或仅通道对照。创建一轮后，每一步都显示动作说明，由用户点击执行；需要抬手时会明确提示。

无手指步骤依次是：信息查询、尾字节顺序、USB 状态、独占、心跳/唤醒、模式恢复前提、缓冲读取、分时重开、单设备 USB 恢复、5 次 libfprint 取消和复位后缓冲对照。随后两次按压完成动作测试，最后一次按压自动完成 A/B/C/D 四阶段。实验序列和手指采样数量沿用有效原始实验；每次新的运行必须独立记录，不能要求其时序或图像变化精确等于历史值。

模式步骤只验证恢复前提；即使将来唤醒得到 ACK，向导也不自动发送 `87` 写入，而保留“未验证”的说明。它能复现本次实际执行的安全测试，不将此前已阻断的危险后续扩展为新的自动操作。底层诊断模块由 GUI 复用，命令行入口供开发调试；旧的独立手指测试入口已移除，日常复现统一走 GUI。

每轮输出到 `build/diagnostics/device-test-<ID>/`：

| 文件 | 用途 |
| --- | --- |
| `report.md` | 可阅读的测试结果、设备信息、各项命令结果及汇总统计，不含指纹样本 |
| `summary.json` | 同轮结构化非生物识别摘要，含完成/阻断/失败与有效性状态 |
| `private/` | 详细 USB 响应、生命周期日志、动作记录、原始图像和严格分析结果，仅留本机 |

新建轮次目录权限 0700，报告与原始文件 0600。每一步和每个手指样本保存检查点；正常停止会等待当前有界传输结束并释放接口，再保存未完成报告。“作废本轮并重来”保留旧证据并标记无效，新轮单独编号；旧数据不会自动并入新分析。突然断电或强制杀进程只能保留最近已保存检查点，不保证最后一次写入完整。

语义拒绝与标准控制请求 STALL 会作为结果记录；Bulk 传输、长度、BCC 等异常终止本轮，后续步骤保留待执行，不盲发命令。测试窗口关闭后预览保持暂停，由用户点击恢复。测试不会录入系统指纹，也不改变当前旁路匹配逻辑。

手指分析会核验保存的响应与实际 IN 字节一致、长度/BCC/状态成立、样本文件与私有记录匹配，拒绝未完成、作废或篡改记录。仅分析显式指定的一轮，不扫描目录合并历史轮次。

## 9. 尚未完成的能力和下一步

1. 将普通与扩展访问纳入同一个 libfprint 串行状态机，区分接触、就绪与消费；先保留两个图像通道的身份，不假定载荷等价。
2. 测最高新样本速率、首帧稳定、长期连续接触和过热表现；不能用主机传输耗时直接计算额定 FPS。
3. 验证读图中途取消、协议异常后的重同步、进程崩溃与系统 suspend/resume；现有成功只覆盖等待手指取消和有限 USB 生命周期。
4. 恢复当前 HT32 固件的真实唤醒与初始化机制，再评估深睡、手势与模式效果；不绕过恢复前提。
5. 确定图像尾字节、加密标志、UID、寄存器索引与错误码语义；不补零、不扫未知寄存器。
6. 校准、自检、ADC 有效位数、物理 DPI、真实质量/匹配精度及设备模板能力仍缺协议或专项证据。
